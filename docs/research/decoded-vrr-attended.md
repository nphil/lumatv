# Internal 4K120 VRR: attended qualification

**Decision: no timing experiment yet.** The stock display controller has separate pixel and timing selections. There is no demonstrated path from a completed internal 4K picture to the next transmitted frame. That does not prove a display firmware change is necessary, or that one would suffice. The current LumaGame feeder submits compressed data; it cannot return a retained decoded picture or its release cookie. The [host presenter and paired test](decoded-vrr-4k.md) do not change the retail backend.

### 1. Rehearse recovery with stock software only

Approval: one attended stock restart, separately from any instrumentation or timing change. No experimental writes. Before shutdown, record the boot ID, boot-image digest, loader options, lack of firmware overrides and working stock picture, sound and Home handback. Use the normal shutdown path and allow OLED maintenance to finish. If its state is uncertain, do not disconnect power.

After power-up, require a **fresh normal load**, not just a new boot ID: the C4 can [resume a snapshot](boot-direct.md). Compare the three [embedded image identities](rea-firmware-result.md) and the read-only `/proc/lg/de/fw-status` against baseline. In the boot log, distinguish `normal` from resume/restore/skip, the header selection for each index (2, 1, 0) from a RAM backup, and final controller readiness from proof of all three copies. In `core/de/vsc_fw.c:400–424,527–546,586–601`, each iteration overwrites the return value; only index 0 reaches the final per-index `done` message. Do not demand nonexistent success messages for 2 and 1, or count the summary as verification of them. Missing independent evidence for either image leaves recovery **functionally demonstrated at most**, not a verified restoration of all bytes. Do not write the firmware-history control to manufacture a receipt.

Repeat stock 50/60-family and 4K120 playback, check sound and picture, exit to Home and confirm normal ownership. Stop on any mismatch, lost link, missing provenance or failed handback. A verified physical cold boot could recover volatile code independently of a wedged MCU; it cannot undo panel damage or restore a live session. A reboot during a later trial is a failed handback, never normal cleanup or an automatic action.

**Operator run sheet (stock rehearsal only).** With the owner present, take the TV lease at Home; stop if another owner, playback or OLED maintenance is active or uncertain. Save these reads off-device before shutdown and after startup: `/proc/sys/kernel/random/boot_id`, `/proc/cmdline`, `/proc/lg/de/fw-status`, SHA-256 of `/boot/Image.lz4-5.4.268-329.ptl4tv.2`, presence/absence of `/var/firmware/pqefw{0,1,2}.bin`, and the boot log without clearing it. Expected: kernel digest `3e13cfe557ad8037972c77f03bd4d8d226e2f58eee0127fd38a98ae23fa52ca8`, `year:24`, `fw_opt:none`, `usr_opt:none`, `usr_num:0`, no overrides. Record a known stock scene, rate, sound and exit to Home. Perform one normal shutdown, allow panel care to finish, then an attended cold start. Repeat the same content and handback; record pass/fail separately for **functional recovery**, **fresh embedded-image selection** and **active byte identity**. Unknown is not pass. Release the lease; the rehearsal authorizes no next stage.

**Receipt commands.** The [collector](../../game/vrr-probe/recovery_snapshot.sh) is a fixed, read-only POSIX script. The authorized TV operator runs it via the approved transport with a 30 s outer timeout, at awake idle on Home, saving stdout and stderr separately on the host. Nothing is installed. An error, timeout or missing final boot ID stops the rehearsal. Store private receipts with mode 0600. On the host, from `game/vrr-probe`:

1. Save the first capture as `before.txt`. Run `python3 -B recovery_check.py baseline before.txt`. Only after a pass, play the known 50, 60 and 4K120 scenarios, return to Home, then run `python3 -B recovery_check.py observe before.txt > before.json`. Prompts record human observations; the program does not launch content.
2. Perform the attended stock shutdown/cold-start step above. Save the second capture as `after.txt`. Run `python3 -B recovery_check.py baseline after.txt`. Repeat the same scenarios and record `python3 -B recovery_check.py observe after.txt > after.json`.
3. Run `python3 -B recovery_check.py compare before.txt after.txt before.json after.json`. Exit **1** is failure. Exit **2** means stop with missing evidence, even if functional playback passed. Fresh header selection, active RAM identity and selector restoration are distinct results. The optional `--states before-state.json after-state.json` compares independently collected `cache`, `pulse`, `pixel` and `timer` unsigned words separately; each file must identify the same logical `owner`, the corresponding `boot` ID and `receipt_sha256`. No retail source for these raw observations is qualified. Do not create them from expected values. No result authorizes a timing change.

### 2. Qualify the observer without changing output timing

**New candidate: `CRC_TOUT`.** The public O22 driver assigns a dedicated hardware interrupt, distinct from `CRC_VOUT0/1` (`chip/o22/os/linux_irqs.h:163–171`; `chip/o22/slt/slt_o22.h:100–103`). The handler reads the pixel checksum and stores host monotonic microseconds **on every second handled interrupt**, up to 150 samples; it acknowledges status. The timestamp is taken in software, not latched at the wire (`slt_o22.c:110–163,203–221`; `include/slt_kapi.h:70–76`; `core/base/os_util.c:580–586`). Even with one interrupt per scan, alternating 10/16 ms and fixed 13 ms both give 26 ms between saved timestamps. Opening the factory device enables checksum hardware; it is not a passive read. The O22 webOS TV build disables the driver (`platform/o22_webos_udtv/platform_dev.mk:3`; `core/modules.mk:31,72`). Retail `de_proc_slt_status` prints queued strings, not these samples (`0xffffffc010924830`; `core/de/de_proc_slt.c:97–125`). The MCU's `[crc0]`/`[crc1]` dump compares two memory buffers (`0x502ca4f0–0x502ca526`, `0x502ca951–0x502ca9bb`); it is not a receiver acknowledgement.

**Can a different observer just listen?** In all 24 saved [Home, HDMI and Netflix interrupt inventories](ambient/), `GICv2` hardware IDs 173/180/181 (VOUT0/VOUT1/TOUT) have no listed action; 104 and 175 do. The factory owner separately enables the checksum unit and interrupt, and acknowledges status (`slt_o22.c:205–219,225–252,306–314`). A software listener can timestamp interrupts already delivered, not create a stream from an inactive source. This rules out passive TOUT capture in the recorded configurations, not the silicon's capability. Retail `DE2VSYNC` (175) is not an alternative: on O22 its handler branches into the shared IPC dispatcher (`0xffffffc01093c410–c454`, `0xffffffc01093b9a4–b9e8`), which tests multiple status bits. Counts include events other than display timing.

**The [Game Optimizer dashboard](rea-game-dashboard-result.md) reports input timing.** Its FPS widget copies `vrrInfo.frameRate` from `utp.extinputs/getVRRInfo`, with the external pipeline ID and a requested 1,000 ms update interval (`QuickSettings/Controllers/GameInterfaces/Interfaces.qml:499–507`, `AppServices.qml:157–162`). With an internal app in front, the saved bind/getter receipts return errors, not panel timing. The O22 OLED uses V-by-One to a **panel-side** timing controller. LG's panel driver contract exposes link lock, not a returned frame sequence (`panel-controller.rst:145–159,738–748`). None of these observations excludes a separate receiver-side diagnostic.

Approval: witness-only, after identifying an actual retail owner and the tap's position relative to the V-by-One transmitter. Prefer a receiver frame-start record; otherwise require a documented transmitted boundary with calibrated phase, **including repeated pictures**. A controller reporting its own timing request is not independent. With stock fixed 120 and 60 Hz output, capture every event, a monotonic time bound and the tagged picture identity. Hold one dim picture for several scans; then change picture IDs at 60 pictures/s on 120 Hz output. Require two events per picture in the latter control, one per repeat in the former, and no unexplained gaps, overwrites or variable timestamp delay that obscures a 2 ms shift. Known rates alone do not establish where the tap sits. Stop if any requirement fails. No factory diagnostic, new driver or blind polling is part of this plan. A transmitter witness proves digital delivery only: the panel may retime the picture after receipt.

### Discovery before any picture-triggered trial

**A. Identify the observation point first.** During ordinary stock modes only, compare each *already acquired, non-destructive* candidate frame event to ready/selected IDs, the tracker wait state and mixer IRQ 104 on one clock. Use a held dim picture, 60 distinct pictures/s on known 120 Hz output, and a verified fixed 60 Hz output. A frame-boundary candidate must count repeats (120, 120, 60 events/s at those output rates), not just picture changes or every second interrupt. Equal rates across all stages do **not** locate the tap. Require either a receiver/transmitter contract or a second independently identified digital link reference in a control where tracker and link differ. If both are absent, label the candidate *unlocated*, even with perfect correlation. No new register reader is qualified: sampler time bounds and dropped/acknowledged transitions must be known. Do not enable factory CRC, clear latched bits or poll the map-on-every-read getter.

**B. Map one reference, not all 256 selectors.** This is an attended design, **not a runnable command**. Preconditions: recovery qualified for the intended change; an exclusive stock owner for both reference and timer, exact original arguments/readbacks; a held dim decoded 4K SDR picture; an already-active tracker wait observed under normal policy; independent confirmation that disconnect returns to stock within two 120 Hz periods. If the tracker never waits at baseline, this trial cannot answer which edge releases it. Do not force readiness. Neither a callable application interface for these owners nor the independent bound has been demonstrated.

1. Keep the pixel selector and decoder clock unchanged. With memory timer 0 demonstrably unused and disconnected, use **only** its owner `(channel, numerator, denominator)`: `(0,8000,100)` requests 80 Hz, period word `5000000`; `(0,6400,100)` requests 64 Hz, word `6250000`. Both rates are inside the observed diagnostic caller's range; this is not a panel safety qualification. The retail routine makes one volatile period store to `0xcc8c0080` and returns zero without waiting for an edge (`0x502b5284–0x502b52a9`). Confirm the *timer edge* and stable period **while disconnected** before each arm. No such edge readback means stop.
2. Hold each trial's period constant. Through the stock main pulse selector only, compare the original decoded reference against the **named** `0x50` (`MSF0`, selector field `0x03`). It updates the software cache then the channel-zero pulse field at `0xcc8c0020`; leave pixels, output geometry, TRK2 policy, interrupt masks, panel clocks and persistent settings untouched. Disconnect before changing period. Interleave the two periods and stock controls; log actual reference edges, individually bounded wait-entry/exit, any link event and IRQ 104. A changed upstream edge followed by changed wait exits only when selected supports that connection. No wait shift with established reference edges and active measurable waits rejects **that selection in that configuration**. IRQ movement alone, coalesced flags or lost lock are inconclusive. Do not sweep aliases or try unknown inputs after a failed arm. Even a positive result with a held picture is wiring evidence, not VRR.
3. On timeout, loss of expected edge, picture, ownership or lock, **disconnect first** via the original pulse-owner argument; only after hardware and cache both match, restore the disconnected timer via its original arguments and verify its exact word. Recheck stock picture, sound, ownership and Home. If either check fails, terminate the programme; the owner decides on the rehearsed cold recovery. No re-arm, raw overwrite, automatic reboot or assumed success from a return code.

**Readback arithmetic, host only.** `python3 -B recovery_check.py split PHASE original.json` prints predictions and exits 2 (no observation). A second file argument compares an actual observation and exits 1 on any mismatch. Phases: `disconnected80`, `selected80`, `disconnected64`, `selected64`, `restored`. Both JSONs carry `boot`, `owner`, `time_ns` (monotonic), `phase`, `cache`, `pulse`, `pixel`, `timer`; numeric fields are unsigned integers. Baseline `phase` is `original`, with `timer_num`, `timer_den` from the timer owner. Baseline must be decoded request `0x20`, pulse field `0x01` and decoded pixel field `0x01`. Bitwise replay for all 32 single-bit inputs gives selected pulse `(original & ~0x73) | 0x03`. At 80/64 Hz the timer words are `0x004c4b40`/`0x005f5e10`. Disconnection restores the **whole** original pulse and cache, not the timer; final restoration restores all four original words. Exit 0 means only that supplied words match; no reader, write or automatic recovery is included.

**Host rehearsal with the actual retail instructions.** From `game/vrr-probe`, with the Xtensa toolchain's `usr/bin` on `PATH`, `$BOOT` the copied retail boot file and `liblz4.so.1` installed:

```
python3 -B check_split_rehearsal.py "$BOOT"
python3 -B split_rehearse.py "$BOOT" --rate 80 > split-host.json
python3 -B paired_evidence.py split-host.json
```

The interpreter verifies the boot and image hashes, disassembles the two stock routines, and restricts stores to private host memory. The baseline words are assumed test values. The check covers 28 runs across 64/80 Hz, including interruption after each of five stores in both directions, deadline expiry, readback disagreement and loss of the controller. The host stops before another arm; for an interrupted disconnect it reconciles the cache and selector before restoring the timer. Unknown state stops further writes. A run has a 100 ms forward budget, at most 96 instructions per call, and separate two-period budgets for the selected reference and the single cleanup attempt. Those are host checks, not hardware deadlines. Receipts retain completed stores, readbacks and abort reasons but contain **zero paired trials**: neither a timer setting nor a host timestamp is a link event. No device backend or live command exists here.

**Why no live shortening or unattended rollback.** At a hypothetical 400 MHz timer, changing `6250000 → 5000000` after `5500000` ticks gives the *same* register readback under four hardware designs. The next edge could occur on the next tick, in 1.875 ms (finish old period), in 12.5 ms (restart), or in 10.736 s (32-bit equality compare after wrap). These are counterexamples, not measured behavior. Separately, instruction replay interrupted the stock `0x50 → 0x20` handback at each of its five stores. A retry before the first store restored `0xa5c5b009`; after the last it was already correct. At all four cuts between cache store `0x4000d4fd` and hardware store `0x4000d6af`, the retry made **no hardware store**, leaving `0xa5c5b00b` with cache `0x20`. A second call is not an independent escape. Cold recovery cannot bound how long the last OLED picture remains on screen. Until a bounded independent disconnect and the necessary event readbacks exist, only the stock rehearsal is ready.

**Recoverable software fault, distinct from an MCU hang.** If the MCU still executes and the exclusive owner can independently read both cache and hardware, the isolated test has just four `(cached source, observed field)` states. Replay of every store prefix in both directions reached all four. For the otherwise stuck `(original, test)` state, submitting the *already selected* test source through its owner, then submitting the original, wrote exactly `0xa5c5b00b → 0xa5c5b009`; no third selector value or raw write was needed. All six interruption points of that corrective first call remained in the same four-state set. This closes **logical reconciliation in the host model**. A same-value register write might still restart a pulse, and loss of the MCU or readback defeats the procedure. It is not a validated live rollback or a reason to relax the independent timeout.

**No demonstrated independent warm recovery.** The formatter's `nosig_duration_de` is an input *size detector* setting alongside missing horizontal/vertical sync durations (`de_cvi_reg_o22a0.h:394–420`), not a documented output deadline or bypass. Retail `ResetDE` returns without resetting; the watchdog tasklets take and release a lock; `IPCisAlive` reads an interrupt-enable bit ([instruction trace](decoded-vrr-4k.md)). None independently forces a stock edge if the display MCU hangs. An attended cold start remains an unqualified backstop until rehearsed, not a bounded in-session escape.

**Stock warm recovery on this build: not qualified.** The host can copy an image without a reply from the old MCU. That is different from forcing a wedged MCU0 to restart and restoring a known scan within a deadline. The retail kernel (`3e13cfe5…`, kernel addresses below prefixed `0xffffffc0`) and retail image 0 (`bc5aa595…`) distinguish three cases:

- **Host reload.** Unlike the published O22 source, the retail downloader branches by index at `10969bc4–10969bcc`: image 0 skips the preliminary halt block. Image 1 enters it, but skips `stall:on` when both SROM maps (1 and 3) already equal `0x50000000` (`1096a068–1096a1dc`). Image 0's release path sets the boot maps, selects SROM, enables trace and clears halt (`1096a458–1096a4d0`). Selecting a reset vector is not asserting reset (`chip/o22/de/de_ipc_reg_o22a0.h:21–36`). A file override changes the bytes selected, not the restart mechanism. `DE_REG_O22_IPCisAlive` samples an interrupt-enable bit (`1096aa90–1096aac0`), not evidence that fresh code ran.
- **Two different watchdogs.** The Linux watchdog really requests a stock reload on an unchanged nonzero count, but its request is explicitly for **image 1 only** (`109522a0–10952304`; `core/de/vsc_wdog.c:298–366`). Image 0 has its *own* `PQE_WDOG_isr`: registration at `0x50322183–0x5032218a`, handler at `0x50322264`. The handler first calls the watchdog routine with zero, disabling its control word. One branch writes `WDOG` and loops; another can call `0x50000000` (`0x50322285–0x50322310`). Both require MCU0 to execute the handler. No evidence establishes an autonomous second expiry with a wired, bounded reset if the handler **cannot** execute. The kernel function named `mcu_reset` is called by `vdec_reset` (`10c8c31c`), in the decoder path, not evidence for the display controller.
- **Standby/resume.** Runtime PM requests suspend/wake and polls a reported flag up to 100 times; timeout does not force a reset (`1094f48c–1094f578`, `1094f5c8–1094f5e4`; `core/de/vsc_fw.c:277–355`). System resume separately tests `IPCisAlive` and can report “already alive” without loading anything (`10951588–109515e0`); its resume path can also reuse the existing bytes rather than copy the header (`core/de/vsc_fw.c:449–487`). Neither a successful wake nor a successful download guarantees fresh execution.

Residual risk: the host may remain reachable while the panel stays black or holds its last picture indefinitely. No bounded, stock, live handback for that fault was identified. A vendor reset-routing guarantee and proof that it restores the output owner, or independent hardware evidence of both, would change that verdict. A healthy cold-start rehearsal alone does not.

### 3. Attempt one off-grid frame, not a mode change

Approval: separate, attended, for one specific reversible timing change. Preconditions: stages 1 and 2 pass; a real backend holds a tagged 4K picture until explicit retirement; and an owner can arm one bounded wait and return to stock even if the app dies. Otherwise no run. No flash, boot override, ForceVRR, change in panel protections or increase in brightness.

**Rejected first experiment: retaining HDMI readiness in the capture-source writer.** Main-window `SetWinPortSrc` (command 82) clears source-state words `+16` and `+20` before installing the port (`0x5028ed1c–0x5028ed37`); old HDMI readiness does not survive an ordinary input selection. For decoded port 7 the stock table at `0x50202998` gives source types `20/21/22/fe` (hex) for attributes 0–3. The first three take the decoded branch at `0x5028efdb–0x5028efe3`, not the capture updater at `0x5028f0c9`; `fe` takes the separate exit at `0x5028f017–0x5028f020`. In command 13 itself the capture updater is called only if `(srcType & 0xf3)` equals `0x10` or `0x12` (`0x5028bd00–0x5028bd1a`, `0x5028bd88–0x5028bda5`). Of all 256 byte values, none passes both this test and the decoded tracker's `(srcType & 0xe0) == 0x20`. This excludes the proposed command-13 activation; other callers of the shared updater are not excluded. Forcing a mode elsewhere would still not supply a timed edge or a picture identity.

An SSH restart is not independent recovery: it requires the host kernel, network and shutdown path to remain responsive, and does not attest to a fresh image load. The [embedded image hashes](rea-firmware-result.md) identify the boot source, not instructions in executing MCU RAM. Without independent recovery, observable active code and an independently bounded release, a volatile change is not a qualifying first experiment.

At stock 4K120 SDR, record the unmodified control. For one trial, keep the pixel source on the decoded picture path. Arm a single wait before the 8.33 ms boundary; release it only when the retained picture becomes eligible, at +11 ms from the previous transmitted frame. The timing producer must not know +11 in advance. Require a stock repeat by +16.67 ms if release fails, enforced independently of the experiment. Record actual eligibility, reference edge, tracker wait exit, every transmitted boundary and ID, and final retirement. A matching ID on an off-grid boundary with no intervening repeat is the first positive result. A fixed tick, an unmatched ID or absent boundary is not. Abort on the first unexpected boundary, lock loss, hang or abnormal handback; restore through the stock owner and verify state. No automatic reboot.

One positive trial warrants the [paired discriminator](../../game/vrr-probe/paired_evidence.py), **not** a VRR switch: +11/+13 ms, unchanged-reference and held-picture controls, full timing uncertainty within the 0.25 ms tolerance. Product qualification additionally requires the usable range, repeats below it, audio sync and stock handback after exit, cancellation and process death. Neither 144 Hz nor a lower VRR limit follows from a 4K120 result.
