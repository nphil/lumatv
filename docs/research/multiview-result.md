## What is established

1. **An app cannot choose the sub window.** NDL has no sink argument (`PUB: NDL_directmedia_types.h`: `NDL_DIRECTMEDIA_DATA_INFO_T.video` is width, height, codec and one unknown int). On webOS 4 an app said `AcbAPI_setSinkType(SINK_TYPE_SUB)`; on webOS 5+ that call sequence is gone (`PUB: ss4s smp_resource_webos5.c` stubs it; `window id` in the load is all the app hands over). The sink a video lands on is decided by the media server and `videooutputd`.
2. **The second pipeline is not special on the wire; what differs is the system state around it.** The media server's policy (`SRC: umediaserver ResourceManager::selectPolicyCandidates`): when a pipeline cannot get the resources it asks for, the pipelines that hold them are ranked by (type priority, foreground, focus, visible, last use) and the lowest ones that hold what is needed are told to release it (`released by policy action`, error 600); the requester and everything ranked above it are never touched. The set's table adds a ladder above that: `levels` = overlay, screen_saver, **multiview**, card, floating, then background (`TV: gfn/tv-2026-10-26/umediaserver_resource_config.txt`): a Multi View app's pipelines outrank a card app's.
3. **Which sink a video gets** (`SRC: umediaserver ConnectionPolicy.cpp, VideooutputConnector.cpp`): `VideoChannelConnection::try_connect` returns -1 unless the pipeline is **foreground** (its app is on SAM's foreground list *and* the pipeline said `notifyForeground`); then it takes the sink the resource manager acquired for it, else the first sink that is free or whose video is in the background, else a sink whose video has no focus. Round 20's finding that `videooutputd` connects a video only for an app id on SAM's foreground list is this rule.
4. **The foreground list is where Multi View shows.** LG's compositor publishes, for each fullscreen app, `multiview`, `pip`, `primary`, `viewType` (`mvsxs` or `mvpip`) and `order` and in Multi View lists both apps (`SRC: /data/home/lgtv/uiinv/qml/qml/WebOSCompositor/services/base/StarfishForegroundAppInfoMgr.qml`); SAM republishes it as `foregroundApps` and the media server parses it (`TV: round 15 journal, compositor/slot-2026-10-28-r15/gfn-browser/B-lumatv/gfn-lumatv-msgs.txt`: `fgAppsEvt: {... "foregroundApps":[{"order":0,"pip":false,"multiview":false,"primary":true,"viewType":"normal",...}]}`). The Multi View controller reads the same list (`mainAppId`, `subAppId`, `viewType`, `is4KHFRSignal`: the same file's `MVC` lines).
5. **The sub window's limits are the codec file's** (`TV: gfn/tv-2026-10-26/device_codec_capability_config.json`, `multiview_sub`): 1920x1088 at 30 for H.264, H.265 and AV1, VP9 at 60; the main window 4096x2304 at 60 (H.265 120). The kernel docs say "Sub scaler is responsible for outputting video to a sub window in the Multi View mode" (`SRC: video-texture.rst`). A 4K120 video occupies both scalers (`V4L2_CID_EXT_VSC_OCCUPATION_SUB_SCALER`, `SRC: v4l2-ext-vsc.h:1938-2011`), and then there is no sub window for anyone (`is4KHFRSignal` is MVC's name for it).
6. **LumaTV's NDL session asks for more than a camera needs.** videooutputd read the feeder's session as `lowDelayMode true`, `isGameMode true`, `subScalerOccupied true` on `MAIN` at 1280x720 and 30 (`TV: compositor/slot-2026-10-29-r20/hwplanes/camprobe-home.txt`). With the policy of point 2 that fits both failures of round 20 [INFERENCE]: a second NDL pipeline asks for what the first holds and, being newer, takes it (error 600 on the first); the foreground app's own id gives the feeder the same rank as the app, and the later one wins MAIN.

## What is not established

- **How the second app's pipeline is told to be the sub one.** Two readings fit what is above: the media server derives it from the foreground list (`multiview`, `primary`, `order`), or the pipeline's client library asks the Multi View controller. Neither is in OSE (the resource manager there has no `levels`); the set's binaries decide it (probe P1: strings of `libmedia-resource-calculator`, `umediaserver`, `libplayerAPIs`, `multiviewcontroller`). Nothing in the repo or in the set's journal has an active Multi View session in it (probe P3 records one).
- **Whether the NDL session's both scalers come from NDL's low-delay load or from its declared ceiling** (on webOS 10.3.1 a pipeline allocates against what the load declares, from another project's lab report on a K24 set: an H.264 load declaring 4K60 refused, the same envelope declared as H.265 accepted).

## The second mechanism: video as a texture (LG's GAV, the four graphic scalers)

LG's own answer to "two or more hardware-decoded videos at once" is not the sub window. `SRC: gp-scaler.rst`: "GAV ... a unified compositor that integrates video rendering and graphic rendering ... Previously, only up to two media could be played due to hardware limitations. By supporting graphic rendering, two or more HW decoded videos can now be played simultaneously ... used for remote meetings, hbbtv ads, YouTube dual video test cases". The path is VDEC -> VDO (`/dev/video27`, `V4L2_CID_EXT_VDO_VDEC_CONNECTING`) -> GPSC (`/dev/video70`: `S_INPUT` the VDEC instance, `S_FMT` the size, at most 1920x1080 NV12 or ARGB, `REQBUFS`, `EXPBUF`, `QBUF`, `STREAMON`, `DQBUF`) -> dma-buf handed to the compositor over Wayland -> a GPU texture; "more than four instances". The set's table has `GP_SCALER 4`, `VTG 1`, pipeline types `vtg` and `vcs`. It is the right shape for a camera tile, but the connection from a decoder to the GPSC is made by LG's GAV pipeline (umediaserver acquires, LSM composites, videooutputd connects); there is no NDL or Starfish option for it that the repo knows. It is read here and left for a probe (P4, read-only).
