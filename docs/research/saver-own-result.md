# LumaTV's saver as the only saver: a "no" to tvpower's question

Built and host-tested (SaverOwn, 2026-10-26). Nothing of it has run on the set. Under LG's compositor LG's Flutter `com.webos.app.screensaver` draws its clock over LumaTV's saver layer in the `Screen Saver` power state (`round8-result.md` row (g)); the saver was drawn on that state, below LG's window. The saver now answers LG's own idle question instead, so LG's saver is never started.

## Resume here

Built (counts under "Checks run"):

- `panels/SaverVote.qml`: puts the compositor on tvpower's screen saver list (`registerScreenSaverRequest`, `{clientName, subscribe: true}`, on `/power2` and on `/power`) while Home is in front and the saver is wanted, and answers each question (`responseScreenSaverRequest`, `{clientName, timestamp, ack}`) with `ack: false`. A list that refuses or does not answer is asked again (5 times at 3 s, then once a minute) and every list is asked anew each time the TV comes on.
- `panels/Screensaver.qml`: `owned` (a question was answered no): the saver draws in the `Active` power state, ends on a key (Home takes the press and its release), on the pointer, when Home is not in front, when the TV goes off, when the owner turns the saver off, and when the video player is woken in its own window. LG's `Screen Saver` state still brings it up and a key still asks tvpower for the screen. A preview (`preview()`, the scenes and tests) never asks the video player: the art's start reads the settings themselves, as `forced` is set before the binding that follows it has run.
- `panels/SaverVideo.qml`: the player's own wake (`a key or the pointer…` in its status) is a `woken()` signal, not a failure; the status is read twice a second while playing (it was every 2 s).
- Owner's switch: `lumatv theme set '{"screensaver":{"own":false}}'` leaves LG's saver alone (nothing is registered or voted). Default on. No Settings row (below).

Not done, in this order (each needs the set; steps in "TV check"):

1. The TV check below, first steps 1 and 2: whether tvpower lists the client and honours the no. If LG's saver still starts, "If the no is not honoured" has the two contingencies, both small.
2. The idle timer end to end (step 4), the pointer (step 6) and the video saver in the Active state (step 5).
3. The memory question (step 9).

Evidence tags: `TV:` measured on this set, `SRC:` LG's firmware tree (`/data/home/lgtv/uiinv`), `[INFERENCE]` not run.

## What was built

Order of events on the set (steps 2 and 4 of the TV check watch each line):

1. Home in front, saver on: `SaverVote` calls `power2/registerScreenSaverRequest` and `power/registerScreenSaverRequest` through a `Service` with `LS.appId`, `clientName` `org.nphil.lumatv`. Log: `[SaverVote] on tvpower's list /power2`.
2. The idle timer ends. tvpower sends the question to its list. `SaverVote` logs `[SaverVote] /power2 asked: <payload> -> no (LumaTV's saver draws)`, answers `ack: false` with the same `timestamp`, and `claimed()` sets `owned`.
3. The saver draws over Home (`Layers.qml`, z 95, as before). The power state stays `Active`; LG's saver is not launched; `nop`'s timer repeats every 180 s and each question is answered no again.
4. A key: the key filter takes it (Home is in front with the focus), `LumaHome.key()` hands it to the saver, the saver ends, the release is taken too. No call to tvpower: the state never left `Active`. The pointer: a move of more than 12 px from where it was when the saver came up, a button or the wheel (`MouseArea`, enabled only while `owned`). The video player (focus is in its window): its own wake runs `turnOnScreen`, writes `idle` and its reason; `SaverVideo` reads it within 0.5 s and ends the saver.
5. Home leaves the front, the TV goes off (`screen.on` false), the owner turns the saver off or `own` false: `owned` ends. Leaving Home also cancels both subscriptions, so a question while Home is not in front never finds LumaTV on the list; one already on its way is answered yes. The TV coming on again asks for both subscriptions anew.

Failure behaviour, all open to LG's saver: a compositor that is not running or restarting has no subscription; a subscription tvpower refuses or does not answer is asked for again 5 times at 3 s and then once a minute for as long as the saver is wanted (the input apps ask the same way: tvpower is not ready in every power state); an unanswered question cannot occur (the answer is a call from the same process, made in the signal handler). [INFERENCE] A tvpower that restarts ends its side of the subscription with an error answer, which the same retry takes up; if it sent none, the list is made anew when Home is next shown or the TV next comes on.

## The power state machine

| Part | With the vote |
|---|---|
| Idle detection, the 180 s timer, repeats | LG's, unchanged |
| Which contexts get a saver (video playing, HDMI, Netflix) | LG's: `screenmanager` and the apps vote as before; LumaTV votes only while Home is in front, where the stock answer is "start" |
| Screen Saver -> Active on a key | Not entered over Home; the saver is a Home layer that ends on the key. Over an app (Plex idle) LG's saver and wake are as before |
| `Screen Saver` state seen by others (the helper's `screen.state`, Home Assistant) | `Active` while LumaTV's saver is up. The saver's own state is `screen.state` plus `owned`; the helper does not publish it yet |
| Standby timers: `nop` timer #6 (3600 s), tvpower's | Not touched; the saver's own `standbyHours` timer (default 4 h, `power/powerOff`) runs while it is up |
| OLED care | Panel-side screen shift, logo luminance and pixel refresh are below the compositor and unchanged; the saver keeps its burn-in rules (mostly black, everything moving, 78 % / 60 % brightness, dim over an hour) |
| The video saver's black panel in `Screen Saver` (videoplane-saver-result.md, open item 1) | Not reached: the state is `Active`, where the player showed the print (round 8, `--once`) |

Open consequence: LG's `Screen Saver` state is never entered over Home, so an inventory of tvpower's lists (`getClientList`) is the way to see the vote; `getPowerState` will not show a saver.

## The 34 MB question (`MemAvailable` after the saver)

TV figures (round 8, video saver run, `round8/tv-2026-10-25/log.txt`): `MemAvailable` 772 900 kB before entering the saver (23:40:50), 729 732 at 7 s, 727 568 at 40 s, 731 248 at 70 s, 738 704 kB 5 s after the wake (23:43:50); `CmaFree` 165 124 -> 160 480 kB. The same set read 739 908 kB at 23:35:10 and 737 400 at 23:35:11 with Home idle. Before-to-after is -34.2 MB, but the earlier idle readings are 738-740 MB: the 772.9 is the high one.

- The set's `MemAvailable` moves by 30-40 MB between idle readings minutes apart (739.9 at 23:35:10, 772.9 at 23:40:50, 738.7 at 23:43:50); one pair of readings does not show a loss.
- That run was the video saver: the GPU art pieces were never loaded (`videoFirst` reads the index only), so the 34 MB cannot be the GPU saver's pictures. What ran and ended in it: the player (25 MB RSS, decoder memory, 8.3 MB window buffer), the libraries it loaded, and possibly LG's Flutter saver app (tvpower launches it on the state change; the log shows no `flutter-client` at 70 s, whether it started and was evicted is [INFERENCE]). Page cache is counted in `MemAvailable`; shmem and tmpfs files, such as the run's own captures in `/tmp`, are not reclaimable.
- What the GPU saver holds, from the code: two `ArtPiece` images at most, each `cache: false`, decoded at the size shown (`sourceSize`, at most 1040 x 700 x 4 = 2.9 MB), set to `meta = null` (source "") by `art.stop()` when it goes down, so the pixmap and the texture are released at the next frame (Home's own frame, which is drawn when the saver hides); the index (6 entries) and the shuffle bag stay (bytes); every timer stops with `up` (`timers` is false in the tests); the deck file is written, not held.
- Host check (offline): 20 saver cycles in the QML host (art, in order, a new print every 1.2 s, 1.5 s in the saver, 0.8 s awake, 2.6 s a cycle), `VmRSS` after each, kB. Run 1: 435268, 432796, 436428, 426640, 437948, 427972, 434492, 438040, 428344, 438316, 438468, 435144, 438740, 438848, 429112, 439116, 429392, 435956, 439508, 429780. Run 2: 436092, 433008, 433324, 437304, 427516, 437348, 437456, 437608, 437724, 437836, 434552, 434664, 438256, 435088, 438480, 438636, 435316, 435472, 439024, 439144. Run 3 (a later checkout, whose host reads lower): 423348, 427560, 427608, 428704, 428732, 428568, 425252, 425364, 419024, 425628, 426788, 429288, 419516, 426164, 429668, 426392, 426548, 430048, 426924, 430320. A 12 MB saw tooth in single readings (allocator and collector), no trend: cycles 5-9 average 433.4 and 437.6 MB, the last five 434.8 and 437.5 MB (+1.3 and -0.1 MB) in runs 1 and 2; in run 3 the means of cycles 5-11 and of the last seven are 425.7 and 428.0 MB (+2.3 MB). The test compares those windows of seven (limit 6 MB; the two means differed by up to 3 MB in runs without a leak), which sees a leak of three quarters of a megabyte a cycle or more. Verdict: no leak found in the GPU saver offline; the 34 MB is most likely the set's own baseline swing plus the player and LG's saver app of that run [INFERENCE]. ## If the no is not honoured

- **Contingency A (hide LG's window).** An anchored patch of the shadow module's `views/StarfishScreenSaverView.qml` in the style of `tools/volume_patch.py`: in `onSurfaceAdded`, `element.visible = (item.appId !== "com.webos.app.screensaver")` so LG's app stays alive for tvpower and draws nothing while the vplane window and any other saver-type window still draw. LumaTV's saver then draws on the `Screen Saver` state as it already can; LG's app still starts (Mali, memory) and the video saver still meets the black panel. Not built: the anchors need the firmware's file and the TV's answer to step 2 first.
- **Contingency B (end LG's saver at once).** On `Screen Saver` with Home in front and `own` on, call `turnOnScreen` (LG's own `cancel()` calls `power2/turnOnScreen`; the saver's key path has always called `power/turnOnScreen`, as RemoteUserList does) and set `owned`: LG's app flashes for under a second every 180 s. Not built; a poorer outcome than A.
