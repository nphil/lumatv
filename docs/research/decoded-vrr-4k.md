# Internal 4K VRR: where picture timing survives

**No qualified internal 4K VRR path.** Fixed 4K120 decoding, a 144 Hz display mode, and a variable panel scan for each distinct decoded picture are separate capabilities. For the last one, both the right picture and an independently scheduled scan must be available. HDMI's range is not a measurement of the internal video path.

## Investigation ledger

Scope: one newly ready, retained 4K picture changes the next panel scan, without HDMI. **Ruled out** applies to the stated mechanism and configuration, not the panel's capabilities. **Blocked** means evidence is missing, not that the mechanism failed. A new run or trace of an existing row needs a different input, observable or artifact that can change its verdict.

**Cross-build tracker check — ruled out as a decoded trigger on these call paths.** LG's published `de_fw_pak_o22a0_y25_o22n2.h` (1,814,948 bytes, SHA-256 `39b30a4a928040576f417ec8bb694ab11661909991ab576a20e18b4de8a7a714`) prints `dbl_en` from window word +24 bit 30 (`0x502a0615–0x502a0629`). Retail `bc5aa595…` instead prints `fva` from a five-bit control field (`0x502a09b3–0x502a09c7`, `0x502a0c1e–0x502a0c26`). When nonzero it raises a timing calculation’s lower bound to at least descriptor halfword +12 plus 48 (`0x5026b4f7–0x5026b505`). Both callers mask the source with `0xf0000` and require `0x60000` (HDMI) before reaching those operations; non-HDMI returns (`0x502a03e6–0x502a03fb` and `0x502a098e–0x502a09a3`). Neither operand at these calls is a decoded picture ID, deadline or ready edge. Only a different producer/consumer reachable with internal video would reopen this route.

**Tagged durations without rewriting the stream — positive to the decoder clock, open at scanout.** In LG's related O22 source a single owner can serialize `VO_SET_FRAMERATE_ES` followed by `VO_WRITE_PICTURE`. This is a pair of operations, not an atomic duration argument. The write snapshots the rational rate, the picture cookie and PTS *before* waiting for queue space (`core/vdec/vo.c:660–692,716–734,773–815,1061–1069`); changing the container rate is a different operation. In a host replay of the extracted setter, snapshot and rate selectors, eight progressive 4K tags were queued as `10,16,16,10,16,10,10,16` ms, then the session rate was changed to 50 before consuming them. All eight kept their own rate. With a non-direct 60/60 opening the logical decoder timer matched 8/8; with a 120/120 opening it stayed at 120 and matched 0/8 (`vds/vdisp_core.c:346–351,670–691`; `vds/vrate.c:960–971`). The queue was a host fixture, not a retail decoder or a panel. This is a candidate for a separately owned presenter, not a feature of the installed compressed-input feeder.

**The decoder’s first pulse is a port-start event.** In the published O22 driver, `vds/vdisp_core.c:1096–1115,1136–1141` disconnects and reconnects an output, then enables its timer. Only a previously disabled timer takes the first-pulse arm (`vds/vsync.c:144–161,306–312`); an arriving picture on a running port does not rearm it. The six-channel “1:1 mapping” comment is not a hardware encoding table: the initializer uses `val * 15` for each four-bit field (`hal/vsync.c:76–86,177–186`; `hal/vsync_reg.h:39–48`). Host execution of the published function with initially clear and initially set selectors produced `0xbcdef0` in both cases, not `0x543210`. Channel zero was zero in both encodings. Without the retail decoder's initializer and an O22N2 encoding definition, this proves neither misrouting nor which downstream signal follows a decoder phase adjustment.

**Network frame sync is named on the host but not implemented by this display firmware.** LG describes command 107 as frame control synchronized to network time (`core/de/mcu/de_ipc_def.h:222`). The retail kernel sends 16 bytes with command 107 at `0xffffffc010933e0c–3e28`. Replaying the command comparisons from image 0 `0x50291932` sends 107, signage mode (92), HDMI TX info (93) and dual-output sync selection (69) to `0x50291eb6`: the diagnostic arm says `Invalid DE IPC`, and with diagnostics off the dispatcher returns zero without calling a handler. Positive controls 76, 94, 106 and 109 reach distinct handlers. Command 76's MultiVision routine checks tile dimensions and coordinates (`0x5028c1e8–0x5028c254`); it is not evidence of clock synchronization. This closes the **MCU commands** as a stock decoded-frame trigger, not the separate host-side HDMI TX setup.

**A capture error is not a transmitted-frame receipt.** Retail image 0 has distinct VTG display/source capture labels. Its `VTG write pic_end error` arm (`0x40008ae4–0x40008b10`) marks bits 31:29 of word `+20` in a 36-byte indexed record as 2 and returns an error. The index comes from one byte in capture state, not from a panel receiver. A matching tag in a captured buffer could identify content at the tap; the error bit, and the absence of an error, do not identify a new scan. The stock capture API sets up buffers (`core/de/de_io.c:1826–1855`); it is not a passive timing read.

**The display tap can identify sampled content, not every picture or scan.** LG places `CAPTURE_DISPLAY_OUTPUT` after picture processing but **before** overlay blending (`v4l2-ext-vt.h:548–565`); an ID must be encoded in the video, not drawn by the app. On image 0 the slot byte at input-state `+0x159` selects a 36-byte capture record (`0x5028d00b–0x5028d023`). Status 2 skips publication on this arm. The success path writes the slot at header `+0x128` (`0x5028d1f4`), i.e. reply `+0x90` after the 152-byte request. The retail host reads exactly `+0x90` (`0xffffffc010953324`), applies its offset modulo five, ignores an unchanged multi-buffer slot on a successful wake, and completes the matching queued slot (`0xffffffc0109552c4–52ec, 5501c–5028, 550a4–50b0, 5519c–51c0`). This is not the decoder's picture number. The normal display capture rate getter **reports** 60 for firmware mode 120, 50 for 100 (`0xffffffc010955524–5540`; five-buffer external-8K exception at `0xffffffc0109555e0–5628`). It does not measure cadence.

Host control: FFmpeg decoded `presenter/fixtures/tagged-bframes.hevc`, area-scaled 128×64 to 64×32 and converted ten-bit video to eight-bit NV12. Reading only the 16 luma cells, without timestamps, recovered 80/80 display-order IDs; retaining just the even or just the odd pictures recovered 40/40 in each case, revealing nothing about omitted pictures. This establishes a pixel-only identification method on the fixture, not availability during retail 4K playback, a transmit timestamp or a VRR trigger.

**A/V delay is an estimate, not a scan timestamp.** A retail main-window writer copies the firmware clock into `0x3fff8588 + 0x280/+0x284` (`0x40005de4, 0x40005edd–5eec`). On the same pair, the latency routine returns its cached answer without resampling. On a changed pair it measures elapsed MCU time (`0x4001ee18–ee75`, cycle counter divided by 396), then adds or subtracts whole periods calculated from the input and configured output rates (`0x502667fb–66881`). Neither operand identifies the receiver or a particular decoded picture. The related O22 `GetVideoDelayedTime` wrapper rounds `locked_time`, not the current sample (`hal_vsc_hwrap.c:1792–1818`). The retail host contains an eight-byte request for `0x4f` at `0xffffffc01092f514`; in the traced image-0 dispatcher, 79 goes to **Invalid DE IPC** (`0x50291a1e–1a3c, 0x50291eb6–1eec`), not to the estimator. A separate window-geometry notification caps its reported delay at 16 ms (`v4l2_vsc.c:2742–2759`); that cap does not describe scan timing or the A/V estimate.

**The input-lag calibration detects a real RGB value inside the TV, not at the panel receiver.** Retail image 0 initializes the pointer at `0x50395750` to `0xcc400000`. Its catch routine reads three 14-bit values at offsets `0x548/54c/550` and accepts if **any** channel is within 1,023 of 4,095 (`0x5028a0d0–a146`); a repeated colour can satisfy the same test. These are the DPE LED block's read-pixel R/G/B values, matched to LG's O22 register map (`be_reg_dpe_o22a0.h:1721–1761`). The calibration programs a coordinate (`0x50289f27–9f88`) and changes hardware state; it is not a passive watch. The separate retail picture-quality menu entries named `GetPixelRead` and `SetPixelRead` point to `0xffffffc010b5aae0` and `…aad0`: both simply return zero. This agrees with the compiled-out bodies in `pe_inf_o22.c:2870–2905,2915–2995` and `pe_hw_o22.h:54`. A later pixel tap is useful for separating content latency from upstream capture, but the RGB match alone cannot count held-frame scans, identify transmission time, or control a new scan.

**Both calibration endpoints use software time.** The launch arm configures two IMX-side windows (image-0 pointers `0x50395784/5780` initialized to `0xcc8c0400/0600`), sets up the DPE pixel probe, then copies the MCU clock to `gInputLagStart`. One mode adds a whole nominal input period to that start (`0x50289dca–9e62, 0x50289f13–a01d`). On the RGB catch, firmware does **not** read a hardware timestamp. It computes the distance from the probe's vertical coordinate using the timing descriptor, multiplies by `floor(1,000,000 / configured_output_Hz)`, divides by descriptor `+38`, and subtracts that time from the MCU clock to form `gInputLagEnd` (`0x5028a187–a220`). Thus even the measured-colour path assumes a nominal line time. It spans marker setup to internal detection, not picture-ready to panel transmission; using its reported delay to certify variable scan duration would assume the cadence under test.

**The ordinary IPP handoff has a local timestamp, but the two main writes address capture memory.** `PQE_TASK_Ipp0Manager` stamps the main window before the guards that can skip the call to `0x40017b28` (`0x40005edd–5eec, 0x40005f21–5f50`); that stamp is not an acceptance receipt. `PQE_IPP0_SetAddr` passes `low32(window_clock >> 7)` and the window pointer to the slot publisher (`0x4000566b–5685`). The publisher stores them separately at `buffer + 36 × slot + 64/+76`, advances the write-index history and returns (`0x40013d61–3da8`). The token has 128 µs resolution and is not the sender PTS. After publication, the ordinary calls with client IDs 6 and 40 (`0x400056a5–56ad, 0x400056ec–56f6`) dispatch through table `0x50201668`. The retail names are `MIF_W_M0_CAP` and `MIF_W_M0_2BIT`; they write the luma/chroma addresses from `+56/+60` (plus plane offsets) to `0xcc8c2b2c/2e0c` and `0xcc8c2bcc/2eac`, respectively (`0x4000e627–e63f, 0x4000e88b–e89d, 0x4000e8d9–e8f7, 0x4000ec4b–ec4e`). Those address writes do not carry the timestamp or request a scan. This identifies the write side only; a separately clocked reader can consume the same surface later.

**The scaler can stage a read address before display permission.** In retail image 0, the VSD task takes flag 4 and calls its manager (`0x40009fa7–9fe3`). On the selected arm the manager calls `0x50259ae0` at `0x40009777`. One branch advances the four-bit read index modulo the current ring depth when it differs from the comparison index (`0x5025a6ae–a6f4`); another copies the chosen index into the same field immediately before `PQE_GSC0_SetAddr` (`0x5025ac16–ac32`). There is a path from that address programming to the manager's later check/wait for flag 2, not back to the address call in the same invocation. Under the decoded/MV0 handshake, a decoder event can therefore stage the pixels first. If MV0's flag is already set, the manager need not wait again. Neither flag carries a picture ID. A separate routine (`0x502595a0`) compares stored slot tokens against a current token, then a previous one, with a tolerance of 33 raw units and a nearest-token fallback. It returns a slot, not a deadline; its use by the normal 4K path was not established.

**What the display permission releases.** The flag-2 test at `0x40009dfe–9e07` gates the branch to `PQE_VSD_SetPicInit` or the separately named 8K-direct helper (`0x40009ed8–9ef4`). In the former, the retail `STRT` table (`0x5039651c`) names IDs 20/21/22 `VCP_U0/U1/U2`. Those cases send constants 3/12/48 to `0xcc460004` (`0x40010d0f–0x40010d26`, common store `0x40010ddb`), not a timestamp or interval to the tracker. The related O22 VCP map describes luma/chroma start masks and a choice of main/sub display sync for these consumers (`pe_vcp_reg_o22a0.h:9–31,65–78`). On the traced arm, picture selection precedes permission and group start follows it; no return signal from the group to end panel blanking is established. Likewise, the `CCO_C_INF` and `LED_C_INF` start calls at `0x4001de88–dea1` are conditional on previously sampled LED interrupt status, not evidence of a new decoded picture starting a scan.

**The clock choice at the mixer is downstream.** Two retail setup sequences clear both pairs of two-bit selectors at `0xcc461410[7:0]` (`0x502861c7–86202, 0x50286242–86277`; `0x502865b2–865e7, 0x50286621–86650`). The O22 field definitions name zero “main display sync” for U0/U1 luma and chroma. The four channels thus select the same existing display reference on these arms, not the other way around. The nearby write to `0xcc461408` at `0x5026a5d8–a5f0` clears bit 1 before inserting the shifted value; bit 1 is the U1 display-clock gate, not any of the sync bypass fields at bits 8–11. These are setup operations, not a recording of the live 4K state.

**Where the exact timing stops being the same signal.** The retail display parser (`bc5aa595…`, `0x502ae934–0x502ae955`) saves the raw mailbox numerator/denominator at window `+102/+104`. For progressive mode its helper (`0x502ad790–0x502ad7c6`) also computes `floor(100 × numerator / denominator)` into `+8/+10` on this arm. The main selector (`0x50266a3c–0x50266a7a`) reads `+10` of `0x3fff8588` and rounds rates above 76 Hz to the nearest multiple of four before its remaining policy. Thus 98.25 and 101.75 Hz both enter that policy as 100, although the mailbox can distinguish them. This pair distinguishes a direct rational-rate consumer from the family selector; equal requested families alone would not rule out another path. No transmitted boundary was observed.

**An exact-rate consumer exists, but it is the video encoder.** Retail routine `0x502b5f48` selects the decoded window's `+102/+104` pair at `0x502b611d–0x502b6129`, or explicitly reads it from the main window (`0x3fff8588`) at `0x502b613a–0x502b616d`. The path can shift the numerator and substitutes 1 for a zero denominator. It packages the rate in destination word `+56`, after writing indexed plane addresses, stride and a timestamp (`0x502b625d–0x502b6297`). Its own format strings name `[VENC]`, rate, addresses and PTS (`0x502b62f6–0x502b633b`). This is a concrete example of the unrounded rate travelling alongside picture data beyond the decoder; it is encoder-input metadata, not a frame leaving the panel link. No encoder was started.

**Look-ahead and starvation are not independent arrivals.** The next PTS comes from peeking at a second queued picture on pop (`vds/vdisp_core.c:450–505`), not from a new surface submitted alongside the current one. A bounded pointer trace from the retail manager, format parser, mailbox parser and pointer-forwarding callees (16 functions) found the store to window `+56` at `0x502ae498`, no read traced back to that field, and reads of the *current* PTS at `0x40018108/0x4001810a`. The five apparent `+56` reads in `0x502aecf4` use global `0x3fffaa48`, not the window. The separate queue-underrun indication is positive evidence of a stock sideband: a pop sets or clears it, the normal decoder tick publishes it in mailbox `+4[10:9]`, and the retail parser copies it into window `+92[10:9]` (`vds/vdisp_core.c:516–527,949–978`; `hal/de_ipc.c:405–418`; `0x502ae619–0x502ae62a`). It reports a selection attempt on an existing tick, not the instant a decoded picture becomes ready. The bounded trace does not exclude other consumers through globals, interrupts or hardware.

## What the stock path does

In LG's related O22 `kdriver` source, `core/de/v4l2_vsc_event.c:2204–2209,2224–2235,2266–2276,2411–2418` reads window 0's decoded timing and requests a mode when the source, dimensions, scan type or reported frequency changes. Frequency is derived from the picture's declared rational rate (`chip/o22/de/de_reg_o22.c:3412–3421`), not when it finished decoding. `core/de/v4l2_vsc.c:2434–2463` sleeps 40 ms between passes; there is no multi-sample dwell in that comparison and no hard 40 ms deadline. At 4K120 almost five pictures fit into one sleep. The one-second comparison in `core/de/de_io.c:1003–1009` throttles a **log message**, not a mode change.

For 67 and 72 fps the host selects the same 60 family (`core/de/v4l2_vsc_event.c:2688–2691`), doubled to 120 on this panel class (`core/de/de_io.c:988–999`). Yet [retail measurements](../lumagame-gaming-features.md#odd-rates-and-residue-follow-up-measured) found 67→119.81 and 72→143.84 Hz, at **1440p**, with tracking off. The 144 selection is downstream, not an ARM request for 144. Prior execution of the captured year-24 display-selector instructions (`0x50266a3c`, image SHA-256 `bc5aa595f350a0dc89f6f314c8cfe6977863ab021f7cda133bdf0795bbefd6de`) returned 144 for a stable internal 144 input with readiness zero, and 120 for the same input with forced readiness seven. That synthetic test used **144**, not 72. Neither it nor the 72 measurement establishes the exact 72-family threshold, its hysteresis, or physical lock time. In a separate [50-family transition](framerate-result.md#round-11-when-the-return-to-120-hz-happened), the output stayed at 100 after disconnect and returned to 120 on the next video's new timing; the 50 ms counter samples cannot resolve hardware lock time.

The archived *Game Mode Research* selector receipt (2026-11-01, `vrr-bounded-test-contract.json`) gives a stronger lead than the firmware strings: the normal-mode routine at `0x4001580d–0x4001583f` derives window readiness from **upstream source state**; a source-flag case can produce readiness 6 even when upstream readiness is zero. This does not establish a decoded app that supplies that flag. The source's HFR flag is not evidence for the display firmware's HRR flag. No stock app-level trigger for per-picture internal tracking has been established.

### Matching retail display firmware

The regular boot file `Image.lz4-5.4.268-329.ptl4tv.2` has SHA-256 `3e13cfe557ad8037972c77f03bd4d8d226e2f58eee0127fd38a98ae23fa52ca8`. The [firmware identity and boot record](rea-firmware-result.md#image-origin-and-boot-stage) separates the three embedded payload hashes from the historical live RAM samples. The 1,821,632-byte image 0 starts at decompressed kernel offset `0x1f71028`. Images 0 and 1 start with `06 14 00`, a little-endian Xtensa jump to offset `0x54`; that does not identify the core variant or require custom instructions to explain early disassembly failures. Image 0's [startup copy map](../../game/vrr-probe/split_stock.py) supports the MCU virtual addresses used below. Those addresses are neither physical boot-map values nor evidence that a particular instruction ran during a game.

**Diagnostic text versus executable evidence.** Image-0 *file offsets*, not function entries: `0x02e9cb/02e9da` label VRR readiness; `0x032896/0328f7` label force mode and tracking; `0x039680/0396ae/039751` label upper/lower rates and delay; `0x038ab4/038ad5` label window and overscan errors; `0x0307c4` labels CVI pseudo-sync; `0x055dd6` names the display-mode message. None proves a safe override, an enforced range, or per-picture 4K120/144 scan timing. In the related O22 source, `be/top/be_top_hw_o22.c:1565–1574` encodes a VRR **request** as `uFrameRate=3`; `core/de/v4l2_vsc_event.c:2623–2631` copies HDMI game and link metadata. The latter is not evidence of a call to the former, and neither event is a pulse for each displayed frame. Source numbers need their field names: in `LX_DE_IN_SRC_T` HDMI is 6 and MVI is 7; in `v4l2_ext_vsc_input_src` HDMI is 3 and VDEC is 4.

**What supersedes the earlier HDMI-only hypothesis.** The retail capture-source updater clears readiness for port 7, but a *different* non-HDMI branch can request hardware tracking for the MVT/MVR families. That result is from instructions and host replay, not just the strings. A decoded picture can be staged before display permission; the two traced mixer setups still select the existing display clock. The missing link is a retained, presentation-ready picture releasing the next output scan, independently observed at the panel link. A decoder completion, a flip notification, a forced mode, or a physical power-off proves none of those. The earlier force-mode/source-spoof procedure is superseded, not a test recommendation.

- **The display engine receives two timing words.** The routine at `0x502ae3d4`, called at `0x502af621` and `0x502af636`, copies mailbox `+0x3c` to picture state `+0x34` and mailbox `+0x38` to picture state `+0x38` (`0x502ae48a–0x502ae498`). These match current and next PTS in `core/vdec/hal/deipc_reg.h:188–204`. The copy is not restricted to low-resolution pictures: the early height check permits a progressive descriptor (display mode 3) above 1088 lines. Two timestamps do **not** mean two owned picture buffers. No independent release or scan deadline follows from that copy.
- **The current timestamp is used, not just reported.** `0x40018108–0x40018112` compares the previous and current picture's `+0x34`; `0x4001813d–0x40018162` labels those same operands `prevPTS` and `currPTS`. The conditional path updates source-validity state, not the next panel period. Neither this consumer nor the copy establishes a path from next PTS to a scan request.
- **67→120 and 72→144 are fixed-rate selection.** Offline interpretation of `0x50266a3c` with stable source-validity 3, ordinary internal state, doubling enabled and debug overrides off returned 120 at 67.00, 70.99 and 73.00 Hz; it returned 144 at 71.00, 72.00 and 72.99 Hz. At the higher boundary it returned 144 at 142.00 and 145.99, but 120 at 141.99 and 146.00 Hz. Readiness 7 returned 120 at all ten inputs. The selector rounds its hundredths-of-Hz input before testing for 72 or 144 (`0x50266a45–0x50266a77`, `0x50266b61–0x50266b72`); three is a tested state-field value, not a measured three-frame lock time. These are branch thresholds, **not** panel VRR range limits.
- **The window period is not the panel period.** The controller timing report `0x50269944` reads validity and a 15-bit line count and prints integer `270000 / total` Hz (`0x502699b4–0x50269a11`). In the [90 fps control](../lumagame-gaming-features.md#measuring-the-scan-rate), the main window reported 3,000 lines (90 Hz) while the display engine sent 120.4 sync pulses/s. The window period measures input; the pulse count measures average output, not individual scans or visible pictures.
- **VRR setup is not a per-picture deadline.** The retail calculator at `0x5026b424` reports clock, input horizontal total, ratios, delay and vertical count (code SHA-256 `a197db64bea8697663583883403bf1962c14404d898195335e2f1faa7424246b`). Its direct caller compares timing geometry and mode against saved values, clears a flag on change (`0x502a0a88–0x502a0b49`), skips the calculator while the flag is set (`0x502a0b8e–0x502a0b90`), and sets it after success (`0x502a0c26–0x502a0c31`). This path configures timing on change; it does not demonstrate that decoded PTS controls individual scans. A separate hardware trigger operating after setup remains possible.

**Pulse routing and handback (retail image 0).** The diagnostic at `0x5023ef9c–0x5023efd0` reads the display-pulse source and upstream vertical-sync selector as separate fields. The related O22 `de_ctr_reg_o22a0.h:915–921,2248–2271` names the corresponding fields; its printed physical addresses are not retail addresses. Two located display-pulse delay writers (`0x502404fb–0x50240503`, `0x5028991d–0x5028992b`) preserve the source bit. Neither is a new picture event.

The vertical-sync selector at `0x4000dd8c` remembers the requested value per channel. On channel zero, the normal policy can request either zero or one (`0x400190d5`, `0x40019116`). An instruction replay against modeled memory, starting with both states clear, gave **1, 0, 1, 0 hardware writes** for requests **1, 1, 0, 0**. Starting with hardware set but remembered state clear, a request for zero left hardware set. This is a reproducible reason not to rely on the next owner reapplying a mode after an out-of-band change; it is not an attribution of all earlier ForceVRR residue.

The display geometry writer `0x40011478` takes its timing structure from a fixed firmware location at `0x4000a4dc–0x4000a4e7`. It updates several banks, labels the main vertical front porch at `0x40011636–0x4001164e`, and preserves the upper half of the update-control word at `0x40011515,0x4001155d–0x40011568`. Rewriting that geometry is not evidence of a one-shot scan latch. The next offline discriminator is to trace the **producer** of those porch values and the **event** that takes them into effect separately; neither the source selector nor a changed porch proves that event belongs to a retained picture.

**HDMI feedback versus the decoded-video clock.** In retail image 0, `0x40012ef6–0x40012f42` skips a same-mode descriptor reload. Its six alternate 3840×2160 rows at `0x50203108` have front porches of 8, 8, 458, 570, 8 and 458 lines; every vertical total equals 2160 active + 10 sync + 72 back porch + front porch. These are mode presets, not panel VRR limits. The main-window path at `0x502a098e–0x502a09a3` accepts only source-port field 6; the corresponding field decoder at `0x50241148–0x50241153` names 6 HDMI and 7 MVI. Once stable, the HDMI path reads the tracker’s current input line count and checks a delay bound (`0x502a0a25–0x502a0a56`); when reconfiguring it passes the shared base descriptor *into* the calculator (`0x502a0c18–0x502a0c26`). This is separate live feedback, not evidence of a new base porch per HDMI picture. The exact physical scan latch is unobserved.

For decoded video the related driver explicitly connects the display port to the decoder sync channel (`vds/vdisp_core.c:1044–1066,1113–1115`; `hal/vsync.c:177–186`) and programs periods in 27 MHz ticks, not HDMI line counts (`hal/vsync.c:243–285`). At fixed 120 the period is 225,000 ticks. Under the source defaults, phase correction can move at most 300 ticks (11.1 µs) per update and at most 430 ticks (15.9 µs) either side of nominal (`vds/vsync.c:31–35,390–391,433–445,545–560`). The resulting 8.317–8.349 ms envelope cannot express 10/16 ms intervals. These are **source defaults**, not retail register readbacks. A programmable internal timer exists; neither an independent retained-picture trigger nor permission to vary the stock 4K HFR base rate follows.

**What initiates the geometry write.** The retail display interrupt handler (`0x4001da8c`) snapshots status at `0xcc460010` and mask at `0xcc460014`, then acknowledges the sampled status (`0x4001dc12–0x4001dc1a`). Status bit 0 with mask bit 0 clear enters the `DISP MV0` arm. Status bit 1 with mask bit 1 clear enters `DISP MV1` (`0x4001dd10–0x4001dd4d`), which calls `0x4000a040` without a picture argument. That policy conditionally passes the mode and shared porch descriptor to `0x40011478`. **The MV1 event precedes this write.** Nothing in this chain establishes one event per physical scan, the scan line at which the write takes effect, or a next-scan shadow latch. The same policy is also called during setup at `0x502966ad`. Neither event bit comes from the HDMI input count at `0xcc460b90`.

The setup path `0x5029663f → 0x50286980` supplies two possible MV1 delay values, `0x33000` or `0x1a000`, according to global state (`0x50286d00–0x50286d16`). Their clock units and relation to physical refresh are unknown. It sets bit 28 of the separate MV0 pulse control and bit **17**, not bit 31, of the geometry control word (`0x50286ddf–0x50286dfa`). The related `de_ctr_reg_o22a0.h:889–905` calls bit 31 force-update and leaves bit 17 reserved. This mismatch prevents assigning the retail latch semantics from that header. Nor do the mode presets measure a safe no-relock porch range.

**Where a real picture is identifiable.** The retail `PQE_MVI_GetFormat` path has a conditional publication distinct from the geometry interrupt: `0x502af732–0x502af78b` copies current mailbox luma address, chroma address and **current** PTS (`+32/+36/+60`) into an indexed record (`+56/+60/+64`), then sets flag bit 28 at `+68`. Producer bytes `[0x502af732,0x502af78d)` SHA-256 `377a6bf82795a0cdd75b9c7d2d14a6fd344c9f56db38a3dc3dbd9c9df8c5fff0`. The optional adjacent record (`0x502af78d–0x502af7ce`) reads the **same three fields from the same mailbox**, not a look-ahead surface. Addresses identify reusable storage; neither the copy nor its flag proves ownership until scan, an acknowledgement, or execution in every HFR mode. The related host driver explicitly accepts HFR without a read-done indication and normally uses two retirement slots (`vds/deif.c:80–106,156–164,328–337`). The [loader distinction](rea-firmware-result.md#installed-loader-trust-boundaries) does not change this lifetime.

**Where the scaler consumes the picture.** `PQE_GSC0_SetAddr` (`0x400006e0`) uses a four-bit scaler read index, not the decoder mailbox's eight-bit `frame_idx`. `0x50259c60`, `0x5025ac2f` and `0x5025b37a` load its address and call it. `0x502858aa` is inside a shift at `0x502858a8`, not a caller. The first caller copies the indexed slot PTS before the call (`0x50259c3c–0x50259c63`). The scaler passes the record base to the memory-read dispatcher `0x4000ef7c` for readers 22 and 16. Its two jump tables (`0x50201740`, `0x50201818`) separate index selection from address programming.

On the ordinary slot path, reader 16 (`OSC0`) loads luma and chroma from `base + 36 × index + {56,60}` and programs the address banks beginning at `0xcc4c182c` and `0xcc4c1a2c` (`0x4000fc59–0x4000fcbb`); reader 22 (`FMC`) programs the banks at `0xcc4c1c8c` and `0xcc4c1e8c` (`0x4000fe69–0x4000fe72`, `0x4000feec–0x4000ff1a`). Other arms add layout offsets or, for reader 16, use a separate address table. Both readers conditionally copy slot `+64` (PTS) into the **same MCU RAM word** `0x5039b140` after the address writes (`0x4000fcc5–0x4000fcd9`, `0x4000ff1c–0x4000ff31`). Reader 22 checks slot flag bits 31:29, not the producer's bit 28 alone (`0x4000f15f–0x4000f179`). This links selected slot metadata to hardware address programming, not to a unique decoder frame ID, an ownership acknowledgement or a physical scan. No trace here identifies which branch a live 4K HFR stream takes.

There is a specific HFR boundary: in one decoder arm `0x502aea65–0x502aea72 → 0x502aea9a`, mailbox `+4` bit 27 (HFR) is copied to state `+92` bit **0**. The slot publisher instead requires either state `+4` bits 20/21 or state `+92` bit **7** (`0x502af6a6–0x502af6b4`). HFR alone is not the condition. A trace that observes only the mailbox HFR bit cannot establish publication before `MV1`.

Immediately before that gate, `0x502af6a3` calls `0x502ad904`. At `0x502ada1d–0x502ada39` it sets state `+92` bit 7 from **nonzero mailbox update-info** (`+4` bits 20:18); a later conditional arm can also set the bit (`0x502adbe3–0x502adbe9`). The related host path writes the current plane addresses, sets update-info to 2 when not paused or 0 when paused, then signals the non-GAV display channel (`core/vdec/hal/de_ipc.c:393–434`). Repeats can explicitly clear the freeze flag before the same current frame is submitted (`vds/deif.c:541–559,573–581`). This provides a normal update route into slot publication but not a unique newly decoded picture or an ordering guarantee against the independent `MV1` event.

**Who wakes the picture publisher.** In retail image 0 the `VDEC-CH0 SRC` handler can signal either IPP0 (`0x4001e135–0x4001e13d`) or IPP1 (`0x4001e11e–0x4001e12d`). The IPP source interrupt can signal the same respective flags (`0x4001ccdc`, `0x4001ce06`). The setter ORs masked bits into an event word (`0x50323ca4–0x50323cb3`): two notifications before consumption can collapse into one. The two task loops wait on their respective masks, 2 and 16, then invoke their managers (`0x5025f2fb–0x5025f307 → 0x5025f417`; `0x5025f687–0x5025f697 → 0x5025f6df`). Both aligned manager calls (`0x40005f50`, `0x40008076`) reach `0x40017b28`, whose input-type branch calls the MVI parser at `0x40017c2f`. The notification carries no picture identity.

There is a real but narrower decoder/display handshake. When `(main_state[16] & 0xe00) == 0xa00` (byte offset 16), the decoder handler clears mask 2 and sets mask 4 on `0x3ffeef48`; `DISP MV0` does the reverse (`0x4001e192–0x4001e1c1`, `0x4001dce9–0x4001dcfd`). The VSD task waits on mask 4 before processing, then its manager checks or waits on mask 2 (`0x40009fa9–0x40009fe3`, `0x40009da0–0x40009dfc`). This orders stages of processing under that condition. It neither orders a *particular* picture before `DISP MV1` nor acknowledges a physical scan. The separate `VSD_VAR … PTS` read at `0x40009f3b–0x40009f45` feeds a diagnostic print, not the geometry writer.

**Which timing each diagnostic sees.** The scaler's `VRR vs total count` (`0x40000f2a–0x40000f3b`) reads `0xcc400806`, the upper half of `AD_MON_SYNC_IN_1`: vertical total at the display back-end sync monitor's **input**. The O22 map pairs it with horizontal total at `+0x808`; MCU `0x400125b6–0x400125ce` also accesses its monitor-enable bit (`be/reg/be_reg_dpe_o22a0.h:2602–2628`). That identifies the monitored signal, not its upstream source selection, time in seconds or final panel scan.

The `MV1` diagnostic reads PE1 line number (`0xcc48100c[28:16]`) and PE1 **input** active (`[13]`) in separate loads. Its later `DISP MV1` report reads the low 12 bits of the CVI current line (`0xcc8402c8`) and the compositor's main-sync line (`0xcc46192c[29:16]`). The latter is specified when main-luma interrupt monitoring is enabled, with zero at falling vertical sync. Source: `pe/reg/{pe_cco,pe_cvi,pe_vcp}_reg_o22a0.h:43–49,562–569,1929–1946`, respectively; MCU `0x4001dd31–0x4001dd4d,0x4001dd84–0x4001dda5`. These are handler-time samples from different blocks, not simultaneous edge captures or a measured latch deadline.

The related O22 output driver does not report measured refresh either: `ovi/ovi_hw_o22.c:5685–5720` prints `vbe_outputFrameRate` as 60 for the 60 Hz panel configuration and 120 otherwise, including the 144 Hz configuration. `vbe_lockStatus` instead tests a link-loss counter for the V-by-One panel interface and reports unknown for other interfaces (`:5430–5458`). Neither distinguishes a variable panel scan from a fixed one. The OVI map names a separate output-sync selector and sync generator (`ovi/ovi_reg_o22a0.h:53–77,153–232`), but gives no next-boundary latch contract.

The stock “Randdom Display Sync” diagnostic is not an internal VRR preset. Its bit-9 arm uses the CPU cycle counter, changes only the lower 28 bits at `0xcc460038`, and preserves the selector (`0x502893ae`, `0x50289900–0x5028992b`). This is the MV0 **pulse delay**, not the geometry at `0xcc460020` or the separate MV1 delay at `0xcc46003c` (`de_ctr_reg_o22a0.h:915–930`). Disabling the diagnostic clears the delay rather than restoring its previous value (`0x502404ed–0x50240503`). Timing those interrupts could make a fixed scan look variable. Likewise the `[CCO] … VRR … Hz` diagnostic divides a **constant 270,000** by the low 15 bits at `0xcc460b90`; its adjacent valid bit is from the same tracker (`0x5026998f–0x502699dc`). Neither is an independent panel clock.

**The memory-source timer is not the normal output-rate selector.** Diagnostic bit 0 passes `(channel 0, 3000…8999, 100)` to `0x502b5284`, which writes `floor(400000000 / rate) × 100` to `0xcc8c0080` (`0x502893ae–0x502893ca`, `0x502b528c–0x502b52a5`). O22 locates IMX control at `0xcc8c0000`; the related layout names offset `0x80` `mem0_sync_period` and has eight source-pulse selectors at `0x20…0x74`, matching the retail initialization addresses (`pe/reg/pe_reg_def_o22.h:204`, `de/de_ctr_reg_o22a0.h:4171–4202`, `0x502763ba–0x502763fb`). That is a memory-input period, not a decoded-picture ID or a VSD output period. No connection to the next panel scan is established. The similarly named host `SetLowDelayBySourceSync` sends a single mode word. Its O22 driver describes off / HDMI hot-plug / CVI interrupt and, where the clock-selection code is compiled, selects HDMI versus the internal clock, not this timer (`core/de/de_io.c:3184–3199`; `chip/o22/de/de_reg_o22.c:4306–4320,4392–4437,4473–4483`).

Bit 0 also overrides the **input** mux. `0x4000d4e0` caches the requested source type before checking the diagnostic word. On a cache miss, bit 0 at `0x3fffa9d8+72` selects group 3, index 4; on channel zero the writer updates `0xcc8c0020[1:0,6:4]` (`0x4000d635–0x4000d6af`). Requests `0xfe/0xff` select the same pair without the diagnostic. A cache hit skips the override check. No traced edge connects `mem0_sync_period` to the output generator’s porch release; the selector numbers alone do not identify that wire. **Closed as a LumaGame route:** the synthetic period comes from the MCU cycle counter, not a retained picture.

**Internal “HDMI-like” route: separate the pixels from the timing reference.** The O22 capture-input mapper explicitly exits for MVI (decoded memory video) before programming its capture clock; its input choices are HDMI/DSC and analog, not decoder memory (`de_reg_o22.c:1673–1755`, `de_reg_o22.h:73–82`). The “8k feedback path” in `core/de/de_io.c:776–795` sends an HDMI port-selection message, not a decoded-buffer address. Retail CVI pseudo-sync is a real raster generator but not a decoded-video loopback. For a valid capture channel, `0x5026b9b2–0x5026ba4d` clears the sync and pixel selectors and disables the generator before validating the new geometry. Its successful arm rewrites the geometry, enables it, and selects pseudo field, H/V sync, data enable **and all three pixel components** (`0x5026bccc–0x5026be35`; `pe_cvi_reg_o22a0.h:628–685`). The pseudo components are ramps or designated values. This routine does not implement a continuous, timing-only update over game pixels; the effect on downstream lock was not measured.

There is a stronger candidate **without emulating HDMI**. In retail image 0 the source-routing branch at `0x40018e46–0x40018e51,0x40018e96–0x40018ea0,0x40018f7c–0x40018f91` takes the MVT/MVR-family timing selector from state word `+0[27:20]` but the pixel selector from byte `+4`, for the same destination. An offline instruction replay through the first channel-zero stores (`0x4000d6af`, `0x4000da54`), with selector words initially zero, cache misses, no diagnostic bits and no pixel override, gives `(pulse,pixels)` words **(0x01,0x01)** for requests `(0x20,0x20)`, **(0x43,0x01)** for `(0xfe,0x20)`, and **(0x01,0x00)** for `(0x20,0x10)`. This establishes independent upstream selection, not that a mixed tuple is active or that `0x43` reaches the output. The IMX period writer itself performs one store, with no explicit wait, commit, or lock acknowledgement (`0x502b5294–0x502b52a9`). Its observed diagnostic caller requests 30.00–89.99 Hz, never 120; that is not a hardware limit.

**Verdict:** blocked via the traced stock HDMI/pseudo-input routines; unknown as an internal timing-reference design. The decisive missing contract is whether, with MVI pixels retained, the selected IMX edge releases the output tracker's vertical-blank wait at 4K HFR, and whether a period change can affect the intended edge without dropping lock. A period taking effect only after the current interval expires cannot release that interval in response to an unexpected picture. The two selector writes prove neither boundary. A software discriminator must distinguish a late tagged picture from an early one between the same fixed ticks and observe the selected picture, reference edge, wait exit and independent output-link edge; a changing input counter alone is a negative control, not acceptance.

**Split-reference decision test — design only, not cleared to run.**

1. **Proposed actuator, not a stock feature.** Keep the game surface on MVI. The candidate reference is IMX group 3/index 4 (logical request `0xfe`); memory timer 0 is the candidate pulse producer, not a verified mapping. First establish that a known pair of timer intervals moves the *selected source edge* with decoded pixels unchanged. Only then test release: after a tagged, retained picture is eligible, shorten the current wait or emit a single edge. No such immediate-edge command, timer reload boundary, or authorized app mailbox for the pair has been identified. Preloading both deadlines before decode completion tests wiring, not response to unpredictable readiness. Reading stock playback cannot impose either perturbation. This requires a display-owner operation; not an NDL option, a direct register write from the app, or the random diagnostic.
2. **Minimal causal comparison.** One 4K SDR window, same established 120 Hz mode and decoder-reference phase, no mode switches. Keep proposed deadlines hidden from the timing producer until ready. Interleave tagged trials due at +11 and +13 ms after a matched previous output edge, both before the same +16⅔ ms fixed tick. Include the unsplit control, identical picture eligibility with an unchanged reference, and unchanged retained content with a changed reference. On one calibrated clock (combined uncertainty <0.25 ms), distinguish decoder/reference ticks, ready and actually selected IDs with retirement cookies, the selected IMX edge, separately timed TRK2 wait exit, and an independent output-link frame start that also detects repeat scans. Pass this mechanism only if the +2 ms change propagates to the intended output edge with matching picture, without re-lock, loss, or an extra fixed tick; the controls must explain neither the shift nor an ID change. A moving IMX edge with an independently fixed output rejects this candidate **in that configuration**. An unobserved edge or lost lock is inconclusive for wiring. IRQ 104 is mixer corroboration only. No verified software output-link witness is available; IRQ plus app IDs alone cannot decide.
3. **Handback gate.** Take exclusive ownership and snapshot the original logical pulse selector, matching hardware fields, timer-owner arguments and exact period word; leave the pixel selector, tracker policy and panel protections alone. Model the start/stop using the *same stock pulse setter*. With unrelated bits nonzero, replay of `0x20 → 0xfe → 0x20` produced `0xa5c5b009 → 0xa5c5b04b → 0xa5c5b009`; repeating `0x20` emitted no store. A modeled raw-only change left `0xa5c5b04b` after two restore requests: the cache still said `0x20`. On exit, stop issuing requests, restore the original pulse source through its owner, then restore the now-disconnected timer exactly through its owner; verify hardware **and** cached values, link stability and stock playback. A guardian outside the test process must do the same after timeout or child death, including partially applied changes. The cache store (`0x4000d4fd`) precedes the hardware store (`0x4000d6af`); an interrupted MCU cannot be repaired merely by repeating the cached request. No independent recovery path or exact timer-owner round trip on retail has been verified.
4. **Operating verdict: no live test, attended or unattended, with current evidence.** An absent/wrong edge can freeze the last frame or blank the display; repeated sync loss can cause a re-lock loop. A wedged display controller may prevent the guardian from restoring Home. A future trial needs a bounded, independently functioning rollback, an already qualified output observer, explicit approval and the owner present. Stop on the first missing expected edge, lock loss, picture mismatch or failed restoration. No blind retry or automatic reboot; a reboot is a failed handback and requires separate consent.

The timer must be unused by other consumers and initially disconnected from the test window; otherwise the proposed restoration order is invalid. A positive paired result proves one controllable 2 ms displacement at 4K, not the panel's full VRR range or safe product operation.

**The split selector is a fallback, not a named timer input.** Retail `0x502baac1–0x502baacd` names `0xfe` `e_IPP_NOP`; the table at `0x503952ac` names `0xff` `C_IPP_NONE`. Both take the same group 3/index 4 branch (`0x4000d5b6–0x4000d5c0`, `0x4000d62c`). Neither name identifies memory timer 0 as the electrical source. Global `PQE_TOP_Init` calls `0x502963a4 → 0x502763b4`: it overwrites eight selector words and requests `0xfe` on channels 0, 1, 2, 3, 4 and 9 (`0x502763b7–0x502763fb`, `0x502764b2–0x50276559`). This is not an isolated handback. Same-mode `SET_DISPMODE` skips its rate-change notification at `0x50290947–0x50290962`. Neither path establishes exact restoration of an independent timer, even if Home reappears.

**The internal frame converter has an explicit high-rate skip, distinct from VRR.** The archived [TV configuration](live-tv-capture/20-config-dvr-tuner.txt) identifies O22N2, internal FRC, UD, 144 Hz and a V-by-One panel link. Image 0 labels working state `+36[17:14]` `frcRun` and `+36[26]` `vrrOn` (`0x502418c6–0x502418d1`, `0x502418fe–0x50241909`). On the normal policy arm calling `0x40016118`, a rate at `+8` over 6050 hundredths of a hertz returns `−5`, skip reason 20 (`0x400161c9`, `0x40016235–0x4001623b`, `0x400162c1–0x400162d6`); the caller sets `frcRun=0` on that result (`0x4000254f–0x40002569`). Earlier exits and later overrides exist. A decoded progressive 120/1 descriptor supplies 12000 to `+8` at `0x502ae93e–0x502ae947`. This permits high-rate MVI to skip conversion without acquiring HDMI's timing reference. It does not establish the branch taken in a particular stream. The shipping kernel's `BE_FRC_HW_O22_Force_Frame_Rate` is only `mov w0,#0; ret` (`0xffffffc010c53c50`).

**A single `[CCO]` status line mixes two clock domains.** `0x50269944–0x50269a11` prints the compositor's vertical total from `0xcc480b30[15:0]`, but prints its trailing `VRR ... tot (...Hz)` from **tracker** `0xcc460b90[14:0]`, with Hz computed as `270000 / tot`. They are not two panel measurements. The former is a useful comparison point downstream of the selected source, but carries no edge timestamp or picture identity. The O22 panel-link boundary map names `mon_tcon[7:0]` at `0xcc43204c` without specifying its bits, clock, retention or edge sensitivity (`sys/o22a0/bnd_ctrl_dpe_o22a0_reg.h:258–266`); `ovi_reg_o22a0.h:52–65,406–413` names output-sync and monitor selectors without their truth tables. The four-bit V-by-One LOCKN counter counts link transitions, and the chip-info packet's color-temperature/gamma counters advance on parameter updates (`ovi_hw_o22.c:3125–3136,3335–3346`), not once per transmitted frame.

**The decoder mailbox interrupt is not a unique ready pulse.** In the related O22 driver, `vdisp_process_input` records a decoder slot, enqueue clock and sequence, then queues the picture (`vds/vdisp_core.c:1340–1381`). The decoder vsync callback publishes the selected picture; the non-GAV path can send it again even with no newly selected frame (`:947–982`; `vds/deif.c:533–584`; `hal/de_ipc.c:388–432`). The explicit handshake at `:982` is for grouped GAV updates in that same callback. The separate O24N decoder source release has the same enqueue → vsync callback → update split (`drivers/vdec/vds/vdisp_core.c:962–993,1391`); it is corroboration, not the O22 retail binary. On retail DE the channel interrupt wakes the picture manager through a coalescing flag, not an ID-bearing edge (`0x4001e11e–0x4001e13d`). The source therefore has an upstream point to identify *which picture arrived*, but the normal downstream interrupt cannot say *when that picture first became ready*. The traced HFR clock selects 120/1 or 100/1, not a deadline supplied on enqueue ([decoder evidence](rea-firmware-result.md#q2-the-120-presentation-ceiling)).

For internal 4K120, the remaining hardware question is whether an independent edge can release the main tracker's wait while MVI keeps reading the same owned picture. The port-6-only HDMI calculator (`0x502a098e–0x502a09a3`) and the MVT/MVR family selection in normal tracker setup (`0x40012468–0x4001249f`) establish different software paths; neither identifies the physical release wire. The O22 interrupt map identifies the wait transitions, not their producer. A software-only positive result needs the matched picture and changed timing at the **transmitted** V-by-One frame boundary, including repeated scans under a held picture. A tracker transition with no transmitted-edge witness proves only an internal timing change. No continuous polling of the existing OSD IRQ, decoder mailbox or link-lock counter resolves this distinction.

The [attended qualification plan](decoded-vrr-attended.md) separates cold recovery, an independent output witness and a single picture-triggered timing change. It distinguishes the hardware `CRC_TOUT` interrupt from LG's every-other-interrupt factory records and from V-by-One chip-info packet checksums.

**Public source cross-check.** [LG’s OLED65C4PUA catalogue](https://opensource.lge.com/product/list?ctgr=005&subCtgr=006&keyword=OLED65C4PUA) lists five releases. The April 14 webOS 24 WG 4.0 notice names kernel modules `5.4.268-320`; the July webOS 25 WG ReNew 1 notice names `5.4.268-329`, matching the TV. The latter's SoC part 3 is 446,985,594 bytes; the retained copy matches its first and last 64 KiB. Its manifest names the October 2024 `linux-and-kdriver_paluma-5-241025-0301` tree, not a new signal specification. The O22, M23 and O24 VCP headers label TRK2 as “wait VFP VRR” without naming the release wire. A little-endian word-array comparison of 18 O22/M23 display payloads (25,589,840 bytes) found neither an explicit monitor-bit legend in their printable diagnostics nor a literal `0xcc43204c`, `0xcc432040` or `0xcc4401d8`. Computed addresses and undocumented hardware wiring are not excluded.

**Why a high-rate read loop is not an output witness.** Retail `DE_REG_O22_RD` maps eight bytes on each call into the display aperture, reads one word for an aligned address and unmaps it (`0xffffffc010968028–0xffffffc010968058`, `0xffffffc0109680f4–0xffffffc01096811c`). Failure to map returns zero, indistinguishable at the value interface from an inactive bit. The MCU independently acknowledges the sampled VCP interrupt status. If upstream and downstream clocks stay locked across a 120-to-60 Hz switch, rate changes on both are identical; sampling faster cannot establish which side the monitor observes. This experiment could reject an inconsistent candidate but cannot certify a transmitted-frame edge or separate coalesced transitions. No safe polling rate has been established. The missing measurement is an independently identified transmitter boundary in a condition where upstream and downstream timing differ.

**Two false positives ruled out in the retail kernel** (decompressed SHA-256 `0fffb8b098be13810c188f2244458ff81136dbadcb1a97a97d90bf784d06dfe3`, addresses from its embedded symbol table):

- **Output observer:** `_lg1kdrm_probe` passes driver table `0xffffffc012303608` to `drm_dev_alloc` at `0xffffffc010d98f94–98`. Its hardware vblank-timestamp callback at `+80` is null. `drm_get_last_vbltimestamp` reads exactly that slot; the null branch calls `ktime_get`, stores the current software time and returns false (`0xffffffc01064ca98–cac4`). The generic kernel function named `drm_calc_vbltimestamp_from_scanoutpos` is present but is not this driver's timestamp hook. The stock DRM timestamp is not an independent output-link witness.
- **Rollback:** `DE_REG_O22_ResetDE` at `0xffffffc01096aa80` is just `mov w0,#0; ret`: success without any reset. The two `VIDEO_CPU_WDG_FROM_MCU` tasklets at `0xffffffc01093a960` and `0xffffffc01093a9a0` take and release a spinlock and return; neither restores selectors or a period. The “alive” getter at `0xffffffc01096aa90–aac0` samples a configured interrupt-enable bit, not a responding-controller handshake (`de_reg_o22.c:3068–3077`). These three interfaces cannot qualify recovery from a wedged display controller.

The retail MV1 policy calls the rate supplier `0x50266a3c` at `0x4000a175–0x4000a178`. The supplier loads main-state `+10` and rounds hundredths of a hertz to the nearest 1 Hz through 38 Hz, 2 Hz through 76 Hz, then 4 Hz (`0x50266a45–0x50266a7a`). One eligible arm selects 72 for 72/144, 50 for 25/50/100, and otherwise normally 60, with a separate 24 case (`0x50266b61–0x50266bd8`). Later gates can double the selected rate at or below 72; an override table selects only 60/50/48/120/100/96/72/144 (`0x50266bd8–0x50266c6d`). With doubling and no override, 67 → 68 → 60 → 120 and 72 → 72 → 72 → 144 fit the recorded measurements. The runtime branch was not recorded. The caller checks cached mode inputs and conditionally feeds the rate to `MCU_DE_IO_SetDisFmt` (`0x4000a18a–0x4000a1cd`). Its same-row check precedes the descriptor copy. This explains mode-family selection without a per-picture deadline.

**The back-end “VRR(120Hz)” request and the active tracker class are separate.** The O22 host encodes ordinary 120 as 1 and VRR as 3 in the same 16-byte mode message (`be/top/be_top_hw_o22.c:1551–1575`, `be/fwi/ipc_def_o22.h:193–198`). Retail `MCU_BE_IO_SET_DISPMODE` (`0x50290924`) copies the message to `0x5039691c`. One arm checks the old rate for change; the other sets bit 24 in two state words according to **zero vs nonzero**. Neither assignment sets the three-bit class at main state `+20[18:16]`. The retail print at `0x50266c75–0x50266c8d` reads `vrr` from that class and `uFrameRate` from the separate cached message. In an instruction replay of the eligible doubling branch (`0x50266c0d–0x50266c28`, other gate clear), requested modes **0 / 1 / 3** returned **60 / 120 / 120** for a 60 base and **72 / 144 / 144** for a 72 base. The results are selector values, not scans. Mode 3 is neither an observed lock nor a per-picture trigger on this path.

The decoded rate feeding that policy has a concrete producer. `0x502ae934–0x502ae953` writes the result of `0x502ad790` to picture state `+10` and `+8` when the decoder mailbox numerator is nonzero. The helper reads only format `+4` and the numerator/divisor at `+8/+10`: `floor(100 × numerator / max(divisor,1))` for progressive mode 3, twice that result otherwise. The related host driver writes the fraction separately from PTS (`core/vdec/hal/deipc_reg.h:58–63`, `hal/de_ipc.c:388–391`). Host instruction replay returned 12000 for progressive 120/1 and 5994 for 60000/1001. Varying PTS alone cannot change the rate through this helper.

**Decoded video has a stock hardware-tracker request, separate from the HDMI-only calculator.** Main IPP normalizes working state at `0x40005f04` before its picture-manager call at `0x40005f50`. With ForceVRR off, `0x4001580d–0x4001583f` copies the source's three-bit readiness, except that nonzero `disp8K` with zero source readiness supplies **6**. On the non-HDMI branch, `0x40018028–0x4001805a` sets `state[+36].bit26` from nonzero readiness only for MVT/MVR source families (`srcType & 0xe0 == 0x20`; names at `0x50241159`). MV1 can pass this on/off bit and readiness to `0x4001238c` (`0x4000a5b8–0x4000a5e1`). Its guarded update sets `ctrl_sync_gen_mvc_trk0[31]` at `0xcc460b50` from `ready != 0 && onOff != 0`; the firmware calls the result `tracking_en` (`0x400124c6–0x400124d8`, `0x40012569–0x400125b4`, `0x40012622–0x40012637`). A separate ready/source-change arm sets IMX `0xcc8c00a0[6]` for MVT/MVR and clears it for other families. The related `de_ctr_reg_o22a0.h:2628–2634` does not define bit 6. With host-modeled memory, the decoded on/off and tracker-commit blocks produced bit 31 clear/set/set for MVT readiness 0, MVT 3 and MVR 6 respectively. These are mode requests, not observations of the active 4K pipeline. Neither block carries PTS, a surface address or a per-picture trigger.

**Where readiness 3 and 6 come from.** In retail image 0 the main source state is `0x3fff97b0`; normalization copies into `0x3fff8588` (`0x40005de4–0x40005de7`, `0x40005efe–0x40005f04`). The capture-source updater requires main window and port **6 (HDMI)** before interpreting game metadata. Otherwise it explicitly clears readiness, including for port **7 (MVI)** (`0x5028b440–0x5028b45b`, `0x5028b8d1–0x5028b8e5`). On the admitted path, with no inhibiting bits, the priority is generic VRR (byte 74 → 1), FreeSync (72 → 2), then G-SYNC (73 → **3**; `0x5028b534–0x5028b594`). The retail kernel sends command 13 with 100 bytes at `0xffffffc01092d178–0xffffffc01092d190`; MCU command 13 calls `SetCviSrcType` at `0x5029194f–0x50291954`, `0x50291c6e`. The related host `_vsc_cvicfgfromhdmi` populates these fields from HDMI receiver timing (`core/de/v4l2_vsc_event.c:2501,2623–2628`; `include/de_kapi.h:952–958`), not from a cloud session. Readiness **6** has a different source: the normalizer synthesizes it when readiness is zero and `disp8K` is nonzero. The retail formatter for those exact three bits explicitly names **0 = 4K120**, and 1–5 split/HDMI420/FEC/VDO modes (`0x5024184e–0x5024185a`). The stock selector at `0x5025e724–0x5025e7d7` writes zero to both state copies if neither profile bit 15 nor 16 is set. These are mode codes, not “frame ready” messages.

**Game playback controls reach different bits.** The related VO driver puts direct-video mode in decoder mailbox `+4[30]` (`core/vdec/hal/de_ipc.c:312–313`, `deipc_reg.h:53`); the retail parser copies it to state `+92[15]`, subject to a subsequent override (`0x502ae644–0x502ae67f`), not readiness `+20[18:16]`. The retail DE low-delay API separately sends command 73, four bytes (`0xffffffc01092f3b0–0xffffffc01092f3c4`); its MCU handler puts the low bit in source state `+16[2]` and marks the update (`0x50291a03–0x50291a08`, `0x50291cca`, `0x5028c708–0x5028c74d`). Nor is the O22 `SetLowDelayBySourceSync` clock callback an actuator: in this kernel `DE_REG_O22_SetLowDelayClock` logs, stores the requested word in RAM and returns success; its getter returns that same word (`0xffffffc01096ca90–0xffffffc01096caa4`, `0xffffffc01096cab0–0xffffffc01096cb4c`). Neither a successful return nor matching readback measures a clock change. No decoded API-to-readiness or per-picture release follows from these paths; the replay's MVT=3/MVR=6 were supplied test inputs, not observed playback states.

**The decoded mailbox has its own tracker calculator, not a per-picture release.** After copying current/next PTS to state `+0x34/+0x38`, the main mailbox parser calls `0x502ae290` at `0x502ae963` with the same state pointer. This is distinct from the HDMI port-6 calculator. It invalidates a setup flag at `0x5039d314` on source/readiness conditions, changed descriptor state, changed geometry or rate byte, or a change in the sum of state halfwords `+0x232/+0x236` (`0x502ae2b5–0x502ae37b`). A set flag skips the calculator. Otherwise, with nonzero readiness and `state[+28].bits[21:16] ≥ 3`, it calls `0x50280ff4` and sets the flag on success (`0x502ae37d–0x502ae3cc`).

The calculator preserves `0xcc460b50[31]` and programs its lower 31 delay bits, `0xcc460b8c[30:16]` and `0xcc460b88[14:0]` (`0x502810ad–0x50281139`). A host instruction replay with modeled 3840×2160 geometry, 120 Hz, 4112×2250 totals and the enable bit initially set produced **3, 0, 3** register writes: first setup, changed PTS pair only, then a one-unit change in the halfword sum. Changing the sum back with **identical** PTS also reprogrammed the delay. None of these calls read either PTS word. This excludes that calculator as a timestamp-to-scan command, not an electrical trigger downstream.

**The normal tracker policy reads hardware state; it does not supply the release edge on those paths.** `0x400123d4–0x40012461` checks the low half of `0xcc480b30`, current state `0xcc460b98[7:4]` and either `[9]` of that word or `0xcc460b90[15]`. On the guarded state-2/3 branches it sets `0xcc460b84[7]`, labelled `reg_host_reset`, and returns. These are recovery decisions, not picture acknowledgements. The located IMX source-family writer changes `0xcc8c00a0[6]` on a ready/source change; initialization separately sets **bit 5** (`0x50276674–0x50276684`). The O22 map names the register `ctrl_src_dco_mfc` but does not define bit 6. The available O22 VCP definitions identify TRK2 wait rising/falling, not what releases the wait. No verified retail wiring specification in the examined material connects that release to an independent decoded-picture-ready edge.

**Clock diagnostic reuse:** The stock clock-control loop does not use the same phase sample for all sources. It takes `0xcc460b74[31:16]` for source family `0x1x` (CVI), but `0xcc460088[31:16]` for the other branch, including MVT/MVR. It reduces the sample modulo the configured vertical total and keeps ten samples (`0x502a1428–0x502a143f`, `0x502a1702–0x502a1742`). The helper at `0x502a11f0`, called at `0x502a178e`, selects the sample **closest to the target around the wrap**, not the latest edge or smallest raw count. The retail print calls the two inputs MVAFLC and MFLC respectively (`0x502a17f7–0x502a1822`). Neither is a per-scan timestamp or a picture ID.

**The normal oscillator adjustment is a fine trim, not a scan request.** Retail display firmware takes the main-window rate rounded to whole Hz and samples two hardware counters (`0x502a1444–0x502a144f`, `0x502a1744–0x502a177a`). Its center word comes from the picture engine's fractional clock synthesizer, not from a picture timestamp (`0x502a1462–0x502a148f`; O22 `sys/o22a0/bnd_ctrl_dpe_o22a0_reg.h:434–463`); a separate board-mode arm substitutes a constant. Both correction-toward-target and return-to-center limit one step to `floor(center/10000)` before the final upper/lower clamp. The widest limits set by this initializer are ±1% of the **word**, not a measured refresh range (`0x502a14d6–0x502a1539`, `0x502a193e–0x502a19a4`). Instruction replay with center 1,000,000: targets 625,000 and 1,600,000 produced 999,900 and 1,000,100; a target of 1,000,007 was preserved. The gated store goes to `0xcc460090` at `0x502a1b39`. No execution rate, panel Hz per control unit, or decoded-picture trigger follows from this replay.

**The downstream timing selector is separate from capture feedback.** The O22 compositor has independent selectors for outgoing vertical/horizontal sync and vertical/horizontal active video (`fbdev/osd_top_reg_o22.h:278–301`; `os/linux_platform.h:56`). Retail display-clock setup calls `0x50286980` at `0x5029663f`; its store at `0x50286d2e` sets those four selectors to **0,0,6,6**. A second routine at `0x50267740` sets **4,4,6,6**; no direct caller or literal pointer to that routine was found. Neither routine's value proves which source is live in a gaming session. The source-dependent helper at `0x4000b8a0` changes the *capture/feedback* selector in the upper bits of the same register and leaves all four output selectors intact. Thus a source change there is not evidence of an output reroute. The public O22 field definition gives no source names for 0 or 4; neither has been tied to a retained picture.

The remaining five stores in the `4,4,6,6` routine program color ranges and curve points (`0x5026779f–0x502678b8`; O22 `pe/reg/pe_cco_reg_o22a0.h:976–992,1230–1235,1248–1253,1284–1289`). None configures a frame-ready pulse. By contrast, the verified setup path also selects `vsd_top_sync_out_sel = 0` before selecting compositor sync input 0 (`0x50286cec–0x50286d2e`; `de/de_ctr_reg_o22a0.h:1088–1091`). The sequence establishes two configured values, not a wire between them.

**The normal sync-delay call aligns an existing signal, not a new picture.** In retail image 0 the main display policy compares the proposed delay mode with the cached mode and skips the call when equal (`0x4000a8db–0x4000a8fc`). All 25 entries of its dispatch table at `0x502004dc`, plus the out-of-range arm, emit only `{1,3,4,7,8,9,10,11}`. None passes the callee's explicitly labelled 4K100/120/144 modes 5/6, 12/13 or 15/16. The generic 4K choices 4 and 11 instead produce **10 lines + 244 pixels** and **7 lines + 214 pixels** of delay, respectively, in an instruction replay with descriptor field `+36` set to 1100 or 2200. The target is `0xcc462074`; its two halves are documented as line and pixel delay, not inter-frame period (`pe/reg/pe_shp_reg_o22a0.h:202–207`). Both also enable the corresponding active and sync delay generators (`:218–236`). This call receives a mode, not a retained picture or deadline. A constant delay can pass a variable upstream signal; the result neither identifies that signal nor proves the screen is fixed-rate.

**The panel-link presets do not identify the live sync input.** The complete 57-entry OLED-compatible 4K120 and non-wireless 4K144 tables match the retail kernel byte-for-byte (decompressed offsets `0x2260df8` and `0x2261520`). They have identical generator timing, including an eight-line front porch, and clear test-pattern control. Only three entries differ, all in link formatting; the 144 Hz initialization also has clock setup *outside* the table (`ovi/ovi_output_format_o22a0.h:269–337,405–473`; `ovi/ovi_hw_o22.c:682–693,735–751`). Neither table sets the output-VSync selector. The source's explicit `bUseInternalSync` instead accompanies **test-pattern pixels**, and pattern-off clears that control (`ovi_hw_o22.c:3818–3869`). These tables identify neither the boot-selected panel assembly nor a per-picture timing source. Identical porch values are not evidence of identical scan rates.

**An interrupt labelled “Pic End” is not a panel-end timestamp.** The retail geometry writer programs the main-luma position-1 interrupt at `0xcc461910[29:16]` with `descriptor.vtotal >> 3` (`0x40011484–0x400114a7`): 281 for a 2250-line row, not 2250. Position 0 uses active height or active height minus 100 (`0x4000a4fe–0x4000a533`, `0x400117ab–0x400117d4`). Under top-level interrupt bit 16, the handler snapshots compositor status `0xcc461908`, acknowledges the whole sample at `0xcc461904`, and dispatches low bits 0 and 1. Bit 1 leads to “1.ChipInfo Pic End” and a saved time (`0x4001dac9–0x4001daef`, `0x4001dbb4–0x4001dc0c`); it is not the separate top-level MV1 interrupt. The O22 map labels other bits of that status word “long period VRR” (20/21), “wait VFP VRR” (22/23), and display sync falling (26) (`pe/reg/pe_vcp_reg_o22a0.h:1818–1865`). The handler does not timestamp those edges separately. The missing silicon fact is which edge, if any, releases that front-porch wait on internal 4K HFR, and whether the panel scans the matching retained picture on that boundary rather than on the fixed grid. A set bit, a periodic status sample or a calculated interrupt position cannot establish it.

**Multi-view constraint independent of VRR.** `PQE_VDO_SetPicInit` has two guarded error exits labelled “4K HFR + PIP MVIT resource collision”, identifying the competing main or secondary picture path and dual mode (`0x502afd3f–0x502afd88`, `0x502afd9b–0x502afddd`, `0x502aff2d`). Single-window playback is the appropriate control for 4K HFR picture-in-picture failures. This is not a blanket restriction on PiP or on graphics overlays.

The remaining test is whether a fresh next PTS **and its matching retained picture** are available before the last instant the controller can still schedule that scan. The installed app trace stops before that boundary. A queued timestamp alone, a mode change, or a controller frequency average cannot pass it.

**Shortest discriminating stimulus, once ownership and handback are established:** 48 transitions, 24 × 10 ms and 24 × 16 ms shuffled (`random.Random(174)` applied to `[10,16] * 24`), versus 48 × 13 ms fixed. Both last 624 ms. In a no-drop ideal fixed-120 model that shows each picture on the first eligible scan, an initial phase sweep in 25 µs steps produced only 8⅓ and 16⅔ ms visible transitions; mean absolute error versus the shuffled target was 1.48–2.48 ms. A 240 fps camera's 4.17 ms sampling interval cannot resolve individual near-misses by itself. Calibrate the optical scan signal on fixed 120 first, then correlate it with distinct dim picture IDs and target times. If repeated scans of unchanged content cannot be distinguished, report picture timing only. This short test separates mechanisms, not full-range or long-run qualification.

**Paired release discriminator (design only).** With the previous scan and decoder-clock phase matched, compare two otherwise identical cases in which a uniquely tagged, retained picture is already due and becomes eligible 11 or 13 ms after the previous scan, within the allowed range. Both fall between the same 120 Hz reference edges: the next tick is 16⅔ ms in both cases; picture eligibility moves by 2 ms. Record on a common calibrated timebase (target total timing uncertainty below 0.25 ms): actual decoder reference edges, independent ready/selection and ownership of the matching ID, individually timestamped TRK2 wait transitions, and a physical scan witness that resolves repeats as well as visible ID changes. Repeat across phases, including a held-picture control. A release and matching scan that shift with eligibility while the reference does not would distinguish picture tracking from fixed-clock handoff. A release alone only locates an internal boundary. If readiness only appears at the timer callback, both wait edges share one status sample, or repeated scans are invisible, the experiment cannot attribute the release. No current app capture supplies all four observations.

**Software-only output witness.** Retail IRQ 104 is `osd_irq`; its Linux `per_cpu_count` increased by 121 in about one second at Home (flip divider 1). The related O22 `fbdev_hw_o22_cmn.c:1601–1628` checks the selected B/S graphics mixer, not a panel-link acknowledgement. Reading `vsync_event` would itself enable notification; its timestamp and the DRM tick follow the flip divider, and runtime suspend can supply synthetic ticks (`core/fbdev/fbdev_drv.c:2895–2919,2938–2943,2974–2997,3115–3126`). Neither is an undivided scan witness.

[`irq_edges.c`](../../game/vrr-probe/irq_edges.c) opens only `/sys/kernel/irq/<number>/per_cpu_count`, samples for two seconds and writes its CSV after sampling. `irq-edges 104` brackets each observed change in `CLOCK_MONOTONIC` nanoseconds from the previous read's start to the current read's end. An increment greater than one has no individual timestamps. For two unit increments bracketed by `[a,b]` and `[c,d]`, the interval lies in `[c-b,d-a]`. These bounds apply to **interrupt accounting**, not hardware-to-CPU delay. Correlation against held picture IDs at shuffled and fixed intervals can establish per-picture mixer pacing if it excludes the fixed-refresh explanation and variable interrupt latency. Panel-link pacing requires an independently identified downstream counter or a verified one-to-one path; an IRQ sequence alone cannot establish it.

The two-second Home control (`vrr-irq-edges/idle-0414.csv`, SHA-256 `2d7bb1fa435c4307fdbf2fb9eae69b6413e3ecf7e333d7b2783b2f303f262aca`) captured 240 unit increments. **One constant clock and phase fits all 240**, at 119.89156–119.89215 Hz. For edge brackets `[aᵢ,bᵢ]`, the feasible period is the intersection of `[(aⱼ−bᵢ)/(j−i), (bⱼ−aᵢ)/(j−i)]` over all `i<j`. Median bracket width was 0.158 ms; the apparent 10.792 ms interval allowed 8.061–10.949 ms. A userspace read-end timestamp alone would falsely suggest variable pacing.

**Live 4K120 control:** Steam Big Picture, not gameplay; H.265 HDR, Smooth, build `d4128515ed85051f`, capture `1795339332000`. During the two-second IRQ trace, `play()` accepted picture IDs 6–245. IRQ 104 increased by 240 in 239 rows. The 16.704 ms read-end gap contains two increments; the 3.486 ms gap follows a 7.503 ms-wide bracket. Equal counts do not pair frames to interrupts.

With cumulative interrupt numbers retained and the merged row excluded, no constant period and phase fits all 238 unit-increment brackets. The smallest extra peak-to-peak delay range permitting a constant clock is 0.623 ms (subtract/add that range from the lower/upper **pairwise numerators** above). For the last **1.5 s**, all 180 brackets admit **119.77285 Hz with just 7.366 µs extra delay range**, while sender timestamp intervals for pictures fed in that window span **3.689–13.533 ms**. The mixer timing is consistent with near-fixed refresh, not demonstrated tracking. No decoded-surface IDs or panel scan timestamps were captured. The later 60 Hz compositor message changes its flip divider to 2 *after* the trace. Receipt: `vrr-irq-edges/irq-live.csv`, SHA-256 `56ab86effcaa4089544232aeb3843fe64dcc799961786718edd193d0a9462688`, matching streamer/feeder JSON and `trigger-times.txt`.

Two named getters cannot supply downstream scan evidence. `FBDEV_O22_CMN_DetectVSyncClk` reduces a pixel-clock selector to a 60/120 class, not a measured interval (`fbdev_hw_o22_cmn.c:491–515`). `BE_PWM_HW_O22_GetPwmInfo` can **write** the PWM3 control on a changed frequency request and returns mean duty, not a pulse period (`be_pwm_hw_o22.c:695–744`). Neither belongs in a passive panel test.

**Possible software timing witness, not a trigger.** Below the public duty getter, the O22 driver reads raw low/high durations from a pulse receiver (`be/pwm/be_pwm_hw_o22.c:1470–1500`). Its normal control path sets enable and frequency, not the receiver input (`:1299–1304`); the detailed status report omits that input and the received durations (`:1545–1590`). The O22 register map has a transmitter output selector, a receiver input selector and 24-bit samples (`be/reg/be_reg_pwm_o22a0.h:93–104,186–224,649–659`). LG's **O24** map labels transmitter alternatives as digital-video-output VSync, HSync and active data, and receiver alternatives as the external input or any of three transmitters for self-test. It separately names video-to-compositor sync, tracked sync and display-engine sync (`be/reg/be_reg_pwm_o24a0.h:95–103,193–212,637–644`). No O22N2 source establishes whether its receiver taps the signal **after** output selection or only the ordinary pulse waveform, or whether the digital-video-output signal is the boundary transmitted to the panel. Matching field positions do not settle either question. This is not a passive test recipe: no PWM, pin or panel settings changed.

The retail `PWM0 : R … F … FRUN … W …` / `PWM1` log is **not** the pulse receiver. Its source in `0x4000a040` reads the outgoing transmitters' rise, fall and width settings. The independent duty writer `0x502b5cd8` programs the matching edge words and masks the free-running widths to 24 bits. The receiver samples are separate registers (`0xcc46013c/140` for pair 0). Neither the log nor the duty writer identifies a looped-back source. [LG's VRR patent, Figs. 7–9](https://patents.google.com/patent/US11798508B2/en), likewise starts with a synchronizing signal extracted from the input and discusses backlight behavior; it does not identify a C4 decoded-buffer-ready signal.
The documented panel-controller `V4L2_CID_EXT_ID_VBE_FRAME_RATE` getter is also configuration, not measurement. **4K144 and low-rate repeats.** The [captured decoder](rea-firmware-result.md) and related `core/vdec/vds/vdisp_core.c:55,264–277` and `vrate.c:565–575` establish the progressive 120 policy, independently of the display selector. A 144 Hz output can repeat pictures; 144 distinct 4K pictures/s is not established. The internal lower tracking bound, the safe transition into low-frame-rate compensation (repeating scans below that bound), and clean handback have not been measured. Neither an HDMI estimate nor an inferred firmware limit is a panel-care specification.

**Opening rate matters.** In the published driver, a progressive 4K session opened with both rates at 60 and without forced HFR or direct mode retained subsequent codec requests of 120, 100, 62.5, 1000/13 and 50 Hz in a host replay. Opening at 120 instead kept the decoder timer at 120 throughout (`vo.c:579–606`; `vds/vrate.c:633–683`; `vds/vsync.c:357–369`). The normal managed path copies the decoder's reported rate into the picture (`control/callback.c:390–405`; `driver.c:1482–1502`); the separate V4L2 sink forwards planes and timestamps, not that rate (`ipc/local/vo_api.c:397–432`). The feeder supplies compressed bytes and a millisecond timestamp, not a per-picture rate. Two genuine 4K HEVC IDR pictures with their own sequence headers decoded on the host with durations of 1/60 and 1/120 s. This does not extend to rewriting the active sequence header before each predicted picture: [H.265 §7.4.2.4.2](https://www.itu.int/rec/T-REC-H.265-202407-S/en) requires the active SPS to remain unchanged throughout the coded video sequence. Neither result establishes a retail panel transition.

**Phase correction is not a picture deadline.** A pending signed correction is shared across windows and consumed on successful picture staging, not on picture arrival (`vds/vdisp_core.c:719–734`). In host replay of `vds/vsync.c:318–335,501–594`, a single +2 ms request at 120 Hz with the previously measured wider limits and phase correction enabled produced nine adjusted periods, peaking at 8.889 ms, then 8.333 ms again. Disabling the correction or sharing the timer between two owners produced no change. The 90 fps stock control above independently separates the source period from the display pulse period. A variable decoder period is not sufficient evidence for per-picture panel refresh.

**The still-picture input is a separate pixel reader.** The published O22 driver selects CPU source and adds two to the photo port (`vp_kwrap.c:1758–1800`; `de_reg_o22.c:3783`); its timing query still reads `VDEC_INFO` and reports no vertical total (`vp_kwrap.c:1358–1397`). Retail image 0 maps source 8, all four port indices, to subtype `0x32`; one window selection changes it to `0x31` (`0x5028ed9c–0x5028edc5`, table `0x50202998`, `0x5028efbc–0x5028efcf`, `0x5028f199–0x5028f1be`). Neither subtype is the HDMI capture subtype. This identifies the source-selection operation, not a panel clock or a per-picture release.

**Where a stock picture first has an identity.** In the related O22 decoder source the normal driver-managed progressive path creates a live-unique nonzero `vdec_priv`, starts the surface with one reference, and calls `save_decoded_info` **before** `display_picture` (`core/vdec/driver.c:2358–2393`). The `DECO` record includes the public prefix with the key, timestamp and buffer index (`:467–470,2168–2220`; `include/vdec_kapi.h:600,743,773`). Reject negative indices: a `DECO` without a displayable picture is legal (`driver.c:2556–2568`). This is a candidate **ready** record for a separately owned native decoder, not an extra reference for an observer of a managed session. Raw VO maps the caller's cookie to `frame->uid` but still enqueues to ordinary vdisp (`vo.c:731–734,790–819`). Its `DISP`/`DROP` records preserve that cookie, but its 64-entry ring silently omits the record from userspace when full (`vo.c:267–269,412–425,460–487`). Neither a successful write nor an elapsed number of ticks retires a lost cookie. The current compressed-input player does not expose this interface.

**No display edge on ordinary picture commit in this source.** Once the window is connected, successful `vdisp_queue_push` only copies the descriptor and advances the head. The wait-queue wake is on **pop**, to free space for producers (`vds/vdisp_api.c:86–89`; `vds/vdisp_queue.c:97–115,125–142`). The earlier `DECO` write wakes its notification reader (`driver.c:430–460`), not the display controller. The alternate V4L2 sink's work item carries timestamp, decoder key and planes into the same `VO_WRITE_PICTURE`; its remote completion updates poll status (`ipc/local/v4l2_sink.c:830–850,1046–1058`; `ipc/local/vo_api.c:397–432`; `ipc/remote/vo.c:107–117`). Switching to this sink does not move selection off the HFR tick.

**Low latency can discard the supplied PTS.** In `FREERUN_IGNORE_SYNC`, `vpts_check_frame` replaces PTS with `enq_gstc` *before* that clock is sampled (`vds/vpts.c:760–779`; `vds/vdisp_core.c:1373–1380`). For both zero-initialized managed and raw VO descriptors the replacement is zero at this point (`driver.c:1482–1487`; `vo.c:660–668`). The original timestamp is distinct. A nonzero VO drop threshold chooses direct-video mode instead, so this ordering is not evidence that LumaGame's installed path loses PTS in this way (`vo.c:540–556`). The renderer contract requires low latency for **both** decoded and HDMI inputs but specifies VRR activation for HDMI (`documentation/source/renderer/scaler.rst:979–1000,1043–1049`).

**Three apparent shortcuts do not supply the missing edge.** The grouped GAV handshake runs once after visiting all matching windows on a decoder tick; the optional repeat branch also counts an update with no new picture (`vds/vdisp_core.c:80–85,947–982`). The one-shot helper uses four MCU callback timers, dispatched separately from the six display-sync channels (`hal/vsync.c:136–157,334–339,371–392,482–486,501–516`); no caller of the one-shot helper was found in the published decoder tree. Raw VO's `variable_framerate` signal feeds skip-mode logic (`vo.c:736–739`; `vds/vdisp_core.c:346,552`), not an immediate scan request. These are source findings, not a claim that every branch ships unchanged.

**Retail pulse routing narrows the split-reference candidate.** On image 0, channel-zero instruction replay with diagnostics off produced the same selector fields for `0x53`, `0xfe` and `0xff` (`0x43`, group 3/index 4). But the explicitly named `e_IPP_MSF0` and `e_IPP_MSF1` selected `0x03` and `0x23`; `0x52` selected `0x33` (`0x4000d574–0x4000d62e`; names `0x502baa7b–0x502baa88`). Index 4 cannot be identified as memory timer **0** by name or ordinal. The sub HDR source `0x71` and `0x62/63` copied channel one's existing reference fields; `0x60/61` copied channel zero's. Swapping initial channel fields from `(0x11,0x22)` to `(0x32,0x41)` swapped their results accordingly. Main HDR `0x70` selected the constant `0x40` in both cases (`0x4000d59e–0x4000d62b`). A copied reference is not a new clock. The distinct main HDR selector identifies no per-picture trigger. The deciding contract is still the electrical source of group 3/index 4 and its connection, if any, to the output wait. No panel scan follows from this replay.

**Selector coverage and tracker initialization.** With a cache miss and diagnostics off, all 256 channel-zero byte requests were replayed under both initial-reference pairs above. Nineteen wrote constant source fields, five copied existing fields, and 232 did not write the pulse mux. These are selections, not an instruction to emit a pulse. Stock `PQE_TOP_Init` calls the register setup at `0x5029663f`. It preserves tracker enable while setting a fixed delay at `0x50286d83–0x50286d91` and sets `0xcc460038[28]` to one at `0x50286ddf–0x50286dea`. The retail formatter reads that display-pulse selection, tracker `0xcc460b50`, IMX source `0xcc8c0020[10]` and no-signal duration `0xcc8402c0[27:26]` from **four different registers** (`0x5023ef9c–0x5023efd6`). O22's `de_ctr_reg_o22a0.h:916–921` names bit 28 but does not name its two electrical inputs. The selector replay closes the software dispatch question, not the wiring between the selected signal and TRK2's wait exit.

## Cheapest decision before firmware work

`core/vdec/vds/vdisp_core.c:480–505` copies `next_pts` only when another picture is already queued. `:966–978` selects the new frame and updates the display interface **inside the decoder timer callback**. `vds/deif.c:275–276` and `hal/de_ipc.c:275–277` forward PTS and next PTS; they do not announce an independent decode-completion edge. `vds/deif.c:156–165,328–338,578–592,645–655` treats HFR as ready without waiting for a display-read acknowledgement, defaults to two clearance slots and retires old frames. Slot depth is not a supported surface lease.

**A picture can be retained without controlling a scan.** In the related O22 capture driver the native LFBC format copies a *descriptor*, not pixels; `fbc_to_vo` replaces its `uid` with the driver's picture index (`ipc/local/v4l2_vdec.c:572–587`). The capture worker retains the picture; capture requeue looks it up for release (`:759–774,1713–1735,1798–1801`). The sink submits a separate per-buffer cookie and returns it for both displayed and dropped notifications (`ipc/local/v4l2_sink.c:836–850,881–900`, `vo_api.c:343–349`). Neither index nor cookie is a stream-wide picture identity or panel acknowledgement. The installed NDL compressed-input call returns no such lease.

`VO_SET_STEP` is not the missing scan command. It can pop a picture while paused and stage its index and timestamps; the ordinary channel’s plane addresses and interrupt to the display processor are published by the separate update routine inside the timer callback (`vo.c:1343–1351`, `vds/vdisp_core.c:949–978,1509–1525`, `vds/deif.c:275–295,573–581`, `hal/de_ipc.c:237–244,275–277,337–350,393–396,430–434`). A staged new index paired with old plane addresses is not evidence of a new scan. This is a related-source result, not an on-TV stepping test.

First check the existing input and diagnostic paths, not the TV. For one 4K stream epoch, keep source picture identity, its original presentation timestamp and tick rate, and local monotonic times for receive, feed acceptance, independently observed selection/availability, and last permitted use. Missing downstream events mean *unobservable*, not zero drops. A constant-rate encoded stream cannot distinguish adaptive presentation from fixed 120 Hz; arrival jitter alone is not variable source cadence.

For a delayed presenter, let `T[i]` be source presentation times mapped to a common clock, `A[i]` the first permitted use and `R[i]` the end of guaranteed ownership. A necessary interval for a constant delay `D` is `max(A[i] − T[i]) ≤ D ≤ min(R[i] − T[i+1] − tail[i])`, where `tail[i]` includes the required time after the next scan starts before the prior surface can be reused. A missing ID, unknown lifetime or unknown tail prevents a positive result. Passing this inequality for a capture does not prove independent scan scheduling, latency acceptability or panel VRR. Those need a matched variable/fixed control and synchronized controller and optical measurements.

For a later **passive mode check only**, an already-planned playback transition plus the existing main-window source report and bracketed `osd_irq` counts distinguishes the 100/120/144 families. No source launch, register access or debug setting is needed for that observation. It cannot prove on-glass per-picture tracking. No decoder runner, firmware load or TV action is part of this finding.

## LumaGame diagnostics boundary

For GFN, `gfn/engine/crates/opennow-streamer-platform/src/runtime.rs:500–508` has the sender's optional frame index, media timestamp and clock rate before pacing. At `:558–585` the VIDEO message gets the TV's monotonic handover time **instead of the media timestamp**. The engine remembers the association for up to 64 in-flight frames. `:387–402,429–440` correlates acceptance using that handover key, not the decoder's selected picture ID. The feeder rounds the key up to load-relative milliseconds, never decreasing it (`gfn/feeder/src/feeder.c:185–191`), then `gf_ndl.c:263–265` passes that integer to the player. Changing only the display firmware would not restore original source timestamps to this argument.

A diagnostics-only capture can join two fixed-size buffers without changing playback or the VIDEO protocol. On the engine side: load epoch, local sequence number, sender index with validity, raw timestamps and clock rate, keyframe/continuity, sink-entry, scheduled-release and actual handover times. On the feeder side: epoch, unrounded handover key, actual player timestamp, complete-message receipt, first feed call, final return, attempt count, queue depth and accept/drop reason (`feeder.c:383–406,1470–1487`). Both processes use the TV's monotonic clock; the sender media clock is a separate domain. Media deltas must account for wrap and discontinuities.

Ten seconds at 120 fps is about 1,200 pictures. Two preallocated 2,048-record buffers of 80 bytes each would cost 320 KiB in total. The capture must drop diagnostic records rather than stall the game, report omissions, and serialize outside the playback path. No stream content is needed. The [existing frame samples](../../game/crates/lumagame-feeder/PROTOCOL.md#app-lifecycle-channel) have arrival gap, feed delay, queue depth and reason, not a downstream per-picture completion. This capture can distinguish source cadence from local pacing; it cannot by itself pass the surface-lifetime or panel test.

### Doom 4K120 capture: where timing changes

Capture `1795325215376`: H.265, 3840×2160, 120 fps, Smooth, 90 kHz sender clock. Doom, HDR and installed build `ba8eb0aad3eaed9d` are operator-reported; both files say build `unknown`. SHA-256 prefixes: streamer `9128ac2bd1c84260`, feeder `1d670c952680c991`. All 1,202 records paired uniquely by epoch and wire key, with consecutive sender IDs 1–1202, identical sizes at both ends, and one successful player call per picture. The only pacing reset was the opening keyframe. No wrap, retry, omission or unmatched row.

Of 1,201 adjacent sender intervals, **1,040** were reproduced within 1 ms at streamer entry, **679** at the scheduled Smooth release, **674** at actual handover and **625** in the player's timestamp argument. Interval correlation with sender timing fell from 0.908 at entry to 0.256 at scheduled release and 0.210 in the player argument. All 1,202 player timestamps exactly equal the ceiling of the load-relative handover time in milliseconds. The 95th percentile absolute interval error was 5.30 ms at the player. These are differences of intervals, not one-way network delays or pixel times.

**Replay, not TV behavior:** keeping the first player timestamp and adding `ceil((RTP[i] − RTP[0]) / 90)` yielded increasing millisecond timestamps with all 1,201 interval errors below 1 ms (95th percentile 0.77 ms, maximum 0.989 ms). One-millisecond precision is not the main loss in this capture; the choice of clock is. This calculation does not establish audio alignment, decoder acceptance of the new timestamps, or a presentation deadline.

**A 120 Hz panel cannot reproduce every sender interval in this sample.** 609 intervals were shorter than 750 ticks (8⅓ ms), including 237 shorter than 625 ticks (a 144 Hz period). Even with pictures instantly available, an ideal 120 Hz presenter that neither drops a picture nor shows it early would lag the desired timestamp by up to 11.10 ms, starting the first scan on time (`scan[i] = max(T[i], scan[i−1] + 1/120 s)`). This is a finite-trace scheduling model, not measured latency. Sender timing is not proof of new game pixels: all 120 pictures ending in the last source-time second carried at most 300 bytes each.

**Next discriminator:** keep the submission/acknowledgement key independent of source presentation time. Before changing playback, check the audio/video clock anchor and reset rules. For panel qualification use distinct tagged 4K pictures with known uneven intervals *inside* the target range (e.g. 10/16 ms shuffled against 13 ms fixed) and a separate ceiling test. Another pacing-off GFN capture may characterize network arrival jitter, but cannot establish picture retention or physical refresh.

### Sender time as the player's PTS (host prototype)

**Clock anchor.** The app has no sender-side audio/video anchor. Audio's wire timestamp is ignored: the feeder stamps each Opus packet with its own load-relative feed time (`feeder.c`, `feed_audio`), after the streamer's jitter buffer has shaped delivery from local arrival time. Video is stamped from its handover time. The only common clock is the TV's CLOCK_MONOTONIC against the feeder's load time. The missing piece is the server's own relation between the two streams: an RTCP sender report (NTP time against RTP timestamp) for each stream, or one shared stream time. The streamer counts inbound sender reports per track (`gfn/engine/crates/opennow-streamer-transport/src/nvst_sender_report.rs`; the timing capture's `sender_reports` and an `NVST rtcp-sr` log line): `rtcp1` data and the audio track's SRTCP are read in full, video SRTCP only by its clear header, which names the sender but not the times. The NVST control messages seen are Timer, Termination and FramePacingMode, and the SDP's `mapRtpTimestampsToFrames` is only logged. Whether the server sends sender reports, or puts audio and video RTP on one time base, is unmeasured.

**Mapping** (off by default; `LUMATV_GFN_SENDER_TIME=1`). The engine sends a `VIDEO_CLOCK` message (wire key, low 32 bits of the RTP timestamp, clock rate, gap flag) before each VIDEO. The key stays what ACCEPT and DROP name; with the switch off nothing extra is sent and the player argument is unchanged. The feeder (`gfn/feeder/src/gf_vclock.h`) stamps the first picture of an epoch as it would have been stamped, then adds the sender's elapsed time, rounded up to milliseconds, across the 32-bit wrap. An epoch ends at a load, a flush or hold, a reported gap, an RTP step back, a changed clock rate, or a result more than 30 ms after or 50 ms before the default stamp. The next epoch starts at the larger of the default stamp and the last stamp, so stamps never go back. Audio stays on feed time, so that window is the most the prototype can move video against it, and it holds back sender-versus-TV drift (100 ppm is 6 ms a minute). Taken alone it fits EBU R37's end-to-end limits (sound at most 40 ms before and 60 ms after the picture); today's offset on the TV is unmeasured.

**Driver caveat.** Matching sender intervals at `play()` does not guarantee matching queue timestamps. In the published `FREERUN_IGNORE_SYNC` path the queue uses a still-zero enqueue timestamp instead of the supplied PTS; `DIRECT_VIDEO` is a different mode. The active retail match mode is unknown. See [the queue trace](#routes-ranked-for-the-4k-target).

**Result.** The Doom capture replayed through the C mapping (`game/vrr-probe/replay_sendertime.py`): 1,201 of 1,201 intervals within 1 ms of the sender's (625 today), largest error 0.989 ms (9.1 today), 95th percentile 0.77 ms (5.30), no stamp going back or repeating, one epoch (the first picture). The new stamps run 13 ms before to 1 ms after today's, mean −3.25 ms. A one-off host run through the real engine runtime and feeder with the NDL stand-in (not kept in the tree), 60 units on an uneven, wrapping cadence arriving with up to 4 ms of jitter, gave 58 of 59 intervals within 1 ms (switch off: 11 of 59); the miss is a 65 ms start-up stall, which the bound re-anchors.

**Not shown:** A/V alignment on the TV, whether NDL honors the new stamps, panel VRR. **Next, on the TV:** one stream with the capture armed, then read `sender_reports` in `<nonce>-streamer.json`. Reports with a known NTP time on both tracks (`coverage.both_usable`; `ntp_us` is null, never 0, when the time is unknown) give each track's NTP-to-RTP pair, which is the anchor. Reports only heard on the wire (`wire`, encrypted) make SRTCP decryption the next step; none heard on either socket means the engine's paths carry no sender reports. Audio RTP against arrival time cannot give the offset, so it is not the test.

**Per-picture prefix** (host observation; not yet on the TV). The timing capture's `frame_prefix` lists, for each video picture of its first 12 s, the 32-bit capture time at prefix bytes 4–7, the `0x200` sender-paced flag, the `0x201` presentation time, the `0x202` access-unit length, any other extension tag, and the prefix length it declares against what the pinned receiver strips (a fixed 20 bytes for AV1 `0x81`, which would mis-skip a prefix with extra tags). The parsing is OpenNOW main's (`a9de957a5902`, `assembled_video_payload`, `nvst.rs:3311–3399`), which names the fields and documents none: that the capture time is microseconds on a clock of the server's own, that `0x200` marks a sender-paced picture and that `0x201` is a presentation time are [INFERENCE]. The one prefix inspected from the TV (`81 08 01 02`, the capture time, an 8-byte extension) held only `0x202`, no `0x200` or `0x201`. `analyse_capture.py` reports the capture-interval distribution, the paced share (unknown, never 0 %, when no picture carries the flag) and the capture-time drift against RTP time, apart from the sender-report outcomes and from the `NVST cloud-gsync` line. A capture time or `0x200` alone does not show changed pixels, accepted Cloud G-SYNC or a panel scan.

### Cloud G-SYNC: request, server answer, observed timing

**Requested.** The one server-facing switch found is `sessionRequestData.requestedStreamingFeatures.cloudGsync` in the CloudMatch session create, with `reflex` beside it. The official web client builds both from a feature gate: `cloudGsync = platform ∧ fps ≥ minimumFpsForCloudGsync ∧ desired`, `reflex = (cloudGsync ∨ fps ≥ 240) ∧ …` (bundle `vendor.js:243–261`; request `main.js:57214–57229`). The native PC client also needs a VRR display, adaptive vsync, fps ≥ 60 and the `CLOUD_GSYNC` entitlement, and turns Reflex on with it (`main.js:5273–5279,100928–100970`). Vsync is a client presentation setting and is not in the request. Neither the official web client's SDP (`vendor.js:22073–22352`) nor OpenNOW's decoded native ANNOUNCE and control frames (`0x0203` pacing, `0x0204` acknowledgement, `0x0207` QoS) name Cloud G-SYNC, VRR or vsync. LG's own TV app requests neither Cloud G-SYNC nor Reflex (`vendor.js:21476–21622`) and adds a fixed-rate pair at 120 fps on webOS and Tizen, `fakeEncodeFps:120` and `fbcDynamicFpsGrabTimeoutMs:6` (`vendor.js:22134–22137`). NVIDIA lists Cloud G-SYNC for its Windows and Mac apps only ([system requirements](https://www.nvidia.com/en-us/geforce-now/system-reqs/), read 2026-11-22). No `cloudGsync:true` session has been captured upstream; the official Windows capture has `vSync:0`, `reflex:true`, `cloudGsync:false` (OpenNOW `docs/streamer-comparison/video.md:56`). [INFERENCE] What NVIDIA's own native client sends beyond what OpenNOW reproduces is unknown.

LumaGame sent `cloudGsync:false` always (no setting reached it), `reflex:true` from 120 fps, the fixed-rate pair at 120 fps, `framePacing.mode:2` with `feedbackMode:0`, and no display-refresh, vsync or VRR field in any control message. Upstream's timing-v5 report (present delay and vsync interval, `presentation_timing.rs`) is not implemented here.

**Server-accepted.** No capture or log holds evidence. The server's decision is `finalizedStreamingFeatures.cloudGsync` in the session response (`main.js:57217,115280`); the core folds it into `negotiatedStreamProfile.enableCloudGsync`, keeps the request when the key is absent, and logged neither. In current OpenNOW main (read 2026-11-22; the pinned `a49b124` lacks it) a frame prefix can carry a sender-paced flag (tag `0x200`) and the sender's presentation time (`0x201`) (`nvst.rs:3321–3386`). ## Decoded-picture presenter (host model)

Host-only C in `game/vrr-probe/presenter/` (contract: `vrr_presenter.h`) with a real HEVC decoder as the picture source and deadline traces as the scan instants. It adds no production path or second TV decoder, touches no TV, and declares no "request the next scan" call; the unimplemented `vrr_scan_backend` is the named plug point for a hardware trigger. **It is not proof of a panel scan**, only of picture ownership and accounting if a backend returned what it reads. `python3 -B -m unittest -v test_presenter` (from `game/vrr-probe/`) builds it with UBSan and runs 16 cases; it skips without zig or the host FFmpeg (`sh gfn/feeder/third_party/build-ffmpeg.sh`). zig 0.16 has no AddressSanitizer, so the decoder oracle below decides surface lifetime.

**Contract.** A picture is `{epoch, stable ID, source PTS and timebase, local ready_ns, opaque owned handle}` and may arrive in any order. A successful submit moves the handle to the presenter; a refused one leaves it with the caller. Each accepted picture has one retirement cookie, first named in the command that shows or drops it. The backend returns the cookie only when no read of the surface can still happen, for a dropped picture as for a displayed one, as a V4L2 capture buffer returns only when the sink gives its cookie back (the O22 LFBC model above). The scanout and prefetch tail is unknown, so the presenter infers no retirement: the scan that replaces a picture or its IRQ, a drop command, a timeout, a picture count and `capacity` authorise no reuse, and the wire ACK for the compressed unit has no entry point and cannot start, extend or end ownership. The presenter frees a surface only inside the retirement, once. At each scan the eligible picture (ready by then) with the greatest source PTS in the epoch is shown, the newest in presentation order for low-latency play and not the last the decoder returned. Queued pictures with a smaller PTS are dropped unshown, and one that arrives at or below the shown PTS is dropped at once, so the shown PTS never goes back. With none eligible the shown picture repeats (one surface held, retired once when a newer one replaces it); with nothing shown the scan is an underrun. A flush starts a new epoch and drops the queued old-epoch pictures but not the surface being scanned: that stays owned, and scans report it stale and never select it anew, until a verified replacement from the new epoch or a handback. At `capacity` a submit fails and no surface is recycled to make room (backpressure). Shutdown drops the queue and refuses new work; a cookie never returned is a reported leak, and the surface is not recycled on a guess. Refused with an error code: no surface (an ACK alone), a duplicate (epoch, ID), handle or queued PTS, a stale or not-yet-announced epoch, a changed timebase, a scan time out of order, a full queue (pictures awaiting retirement count), a stale, repeated or premature cookie, and re-entry from a callback.

**Ownership proof.** libavcodec from the feeder's pinned host FFmpeg decodes `fixtures/tagged-bframes.hevc` (80 pictures, each tagged in its pixels; Main10, pyramid B-frames, closed GOP of 40) one access unit at a time, so pictures leave the decoder reordered (32 reorderings, 2 access units of lookahead). Each picture is the decoder's own native-format frame, kept by reference count: the presenter reads and copies no pixel. An oracle wraps every plane buffer the decoder hands out and sees the last unref, so it knows when memory returns to the decoder's pool. Over the 18 runs below (nine traces at each of two cookie delays; 1,044 pictures; 1,080 plane-0 buffer handouts over 149 distinct addresses, counted per run, so the pool recycles memory) no recycled memory overlapped a live surface, no live plane buffer was freed, no read through the backend found a changed picture, each release dropped one reference per plane, and nothing was outstanding after close. Separate cases cover duplicates (ID, handle and queued PTS), stale and future epochs, a full queue, flush, a flush that keeps the scanned surface, selection by PTS from 12 pictures in callback order, backpressure with late cookies, shutdown, retire after drop, stale or repeated cookies, a lost cookie and an ACK with no surface: none recycled a live surface or leaked one. A faulty owner that drops its references while the backend may still read is caught (4 of 29 surfaces corrupted or recycled), so the oracle can fail.

**Deadline traces.** Three traces of about 624 ms on the stream's 90 kHz clock serve as both scan instants and source picture times, giving nine runs: fixed 120 Hz (76 instants), the shuffled 10/16 ms intervals above (`random.Random(174).shuffle([10, 16] * 24)`, 49) and fixed 13 ms (49). Each runs twice, because how late the backend returns a cookie is unknown and the presenter never reads it: cookies back at once, or 10 ms plus 0–40 ms of seeded jitter after the replacing scan or the drop command, out of order. The other parameters are assumed, not measured: a picture is ready 2 ms after its source time, the scan trace starts 4 ms after the source trace, capacity 64. Held runs from ready until a newer scan or a drop decided the picture's end, so it does not depend on the cookie delay; interval error is the change between the first scans of consecutive shown pictures minus the change between their source times, absolute; peak owned is the most surfaces owned at once, with prompt and with late cookies. Every picture was shown or dropped once and retired once (displayed plus dropped retirements equal the pictures), none was refused, no retirement failed and none leaked at free. Every scan, show and drop decision is identical at both delays; only the surfaces owned differ. A starved run (capacity 3, cookies 10–50 ms late, the 120 Hz trace as scans and pictures) refused 45 of 76 pictures, showed 31 and recycled none. `sh game/vrr-probe/presenter/build.sh OUT`, then `OUT/presenter_test STREAM.hevc STREAM.order --report` (the two fixtures in `presenter/fixtures/`) prints the table.

**Reading.** A cadence mismatch costs repeats and drops, not ownership: a repeat holds one surface across scans and retires it once, a drop retires without a show. The 120 Hz grid shows the shuffled pictures only on 8⅓ or 16⅔ ms changes (all 48 asserted) with a mean interval error of 1.73 ms, inside the 1.48–2.48 ms of the no-drop fixed-120 model above; 13 ms scans cannot follow 120 Hz pictures (27 of 76 dropped). A trace driven by its own cadence shows every picture once, with zero interval error and no repeat, drop or underrun. A late cookie changes no decision and keeps more surfaces owned (2–3 at most with prompt cookies, 5–8 with late ones), which is what `capacity` has to cover; too little capacity refuses pictures instead of recycling surfaces. These follow from the given instants and assumed parameters. On a panel the scan instants are the unknown, so nothing here says what the panel does.

**Backend feasibility: unsupported on the current TV backend.** LumaGame's authorized path (NDL or the ES player, fed by the feeder) accepts compressed units and returns nothing per picture. `ndl_feed_video` reduces the player's `play()` result to taken or full (`gfn/feeder/src/gf_ndl.c:265–271`); the pipe table offers `feed_video`, `queued`, `flush` and queued PF_EVENT_T events, none per picture (`gf_pipe.h:13–14,44–69`); the one release hook, `on_released`, logs a resource-policy event (`gf_ndl.c:78`). The app therefore sees no decoded picture, handle, ready time, scan event or retirement, and the ES player shows a unit when it arrives (`gf_pipe.h:7–8`). The engine's `Accept` and `Drop` carry the unit's `pts_ns` and are matched by it (`gfn/engine/crates/opennow-streamer-platform/src/runtime.rs:418–441,470–477`): that is the wire ACK, separate from any surface. The stock decoder's buffers are out of reach: the native jail's `/dev` has no `video21` (the stock decoder), `dri`, `dma_buf_te` or `dma_heap` (`docs/research/cardapp-result.md:169`; [INFERENCE] the LumaGame jail is the same mechanism), and the `/dev/video21` capture formats are NV12 and LFBC, which carries no pixels, judged not viable as zero-copy (`docs/lumagame-gaming-features.md:1026–1100`). The one decoded-picture owner in the tree is the feeder's software texture path (`gf_swdec`), a second decoder and so out of scope. The contract becomes deliverable only with a call that returns a per-picture handle with its release event and a way to time a scan (a display-owner operation, as the split-reference test above requires); neither is known on the retail firmware.

**Limits and open choices.** No panel scan, link frame start or TV behaviour is shown; the 128×64 stream and libavcodec's pool stand in for the TV's decoder, and the parameters above are guesses. Untested: any TV, the NDL surface contract beyond the API evidence above, `/dev/video21` capture buffers, 4K surfaces, any real backend. The VRR hardware review settled the model's open choices; they are decisions, not measurements: DROP cookies come only from the backend after every possible read has ceased, with no timeout or ACK-based retirement; a flush drops queued old-epoch work and keeps the scanned surface until a verified replacement or a handback; the newest eligible picture by PTS is shown, not the decoder's callback order; and no tail, count or capacity authorises reuse, so a full queue refuses pictures. Still unknown, and so scenario inputs rather than assumptions: the scanout and prefetch tail, how late the backend returns cookies (modelled as 10–50 ms, out of order), and the real V4L2 capture buffer count against `capacity`.

### Paired-evidence analyzer (host arithmetic)

`game/vrr-probe/paired_evidence.py` applies interval arithmetic to the records of the split-reference test above: tagged retained pictures due at +11 and +13 ms before the same fixed tick, with the unsplit and held controls. It reads records somebody else captured, touches no TV, and **does not close either hardware gate**: a qualified output observer and a bounded rollback remain open, and a record's declared provenance is not verified here. Two complete pairs with worst-case widening discriminate the mechanism; they do not qualify the product, the panel's VRR range or safe operation. `python3 -B -m unittest -v test_paired_evidence` (from `game/vrr-probe/`) runs 19 cases.

**Input.** JSON `lumatv-vrr-paired-evidence` version 1 (schema in the module docstring): a calibrated-clock flag with per-kind `alignment_ms`, whether the link witness resolves repeat scans, and six trials per pair (`split`, `unsplit` and `held`, each at `+11` and `+13`). A trial holds its epoch, mode and lock, the previous, retained, selected and retired picture IDs with the retirement cookie, `admitted` (the pictures made eligible during the trial: the retained one alone, none for `held`, so no selection policy decides what is shown), `ready`, `decoder_tick`, `ref_edge` and `trk2_exit` as `[lo, hi]` ms, and every link frame start from the previous one to the next, repeats included. Each time names its source kind and, for a link start, its source name. Only `link-witness` counts as a link frame start, and only under a qualified name: the registry is empty and a record cannot add to it, so a real record is `inconclusive` (`link_witness_unqualified:<name>`) until a reviewed change qualifies a source. IRQ 104, the TOUT factory CRC and MCU requests are never link witnesses, whatever the record calls them (`link_witness_forbidden_source:<name>`), and no qualification overrides that. `hw-trace` supplies the decoder tick, reference edge and TRK2 exit, `app` or `hw-trace` the ready time. IRQ counts and software vsync (IRQ 104 is `osd_irq`) and the compressed-input ACK, DROP and `play()` times are refused as link evidence; `synthetic` is refused unless `--allow-synthetic`, and the report then says it is arithmetic only.

**Method.** Every delay is measured from the trial's previous link frame start in exact rational arithmetic (interval widths add as worst cases; `alignment_ms` widens further). The paired displacement is the +13 delay minus the +11 delay for ready, decoder tick, reference edge, TRK2 exit and link. It `follows` when the whole interval lies within 2 ± 0.25 ms, is `fixed` within ±0.25 ms, is `unresolved` when it straddles a band and is `other` otherwise. `supports` needs the reference edge, TRK2 exit and link all to follow; `rejects-in-configuration` needs the link fixed while the reference follows; anything else is `inconclusive`. A held picture ends at the first independently observed link start at or after the common fixed tick: every start before the last, each edge and repeat included, must be provably before the tick and the last provably at or after it (`held_end_not_first_after_tick`, `held_end_before_tick`), and a start whose order against the tick is not certain is `tick_order_ambiguous`. A missing or doubtful input never rejects: an uncalibrated clock, unresolved repeats, a mode, epoch or lock change, an unresolved or out-of-order picture ID, an unrecorded or wrong `admitted` set (`admitted_unresolved`, `selection_ambiguous`), a reused cookie, an unqualified link witness, overlapping link brackets, eligibility after the tick, different next ticks in the two arms (a fixed-tick phase alias), a control that moves the link and an unmoved held reference each give `inconclusive` with a reason code. All pairs must agree and number at least `--min-pairs` (default 2); each pair lists its tick delay, so phase coverage can be read off. Two complete pairs with worst-case widening discriminate the mechanism; a `supports` is one controllable displacement in one configuration, not product qualification, the panel's VRR range or safe operation. The paired release discriminator above (no actuator, so `split` and `unsplit` coincide) surfaces as `control_explains_shift:unsplit` with the per-step readings and has no verdict here.

**Use.** `python3 paired_evidence.py trials.json [--json] [--min-pairs N] [--allow-synthetic]` (exit 0 analysed, 2 bad input). For real data: record each trial on one calibrated clock, declare `witness.resolves_repeats` only if the observer detects repeat scans, record the pictures admitted in each trial, and list the six trials of each pair at two or more fixed-tick phases. No link-witness source is qualified, so no real record can leave `inconclusive` yet; neither the command line nor a record can qualify one, only the module's registry or `analyse(..., qualified=...)`, as the tests do. The only data on hand, the IRQ 104 trace and the Steam Big Picture 4K120 H.265 capture `1795339332000`, hold no trial and give `inconclusive`: `python3 paired_evidence.py --historical IRQ.csv STREAMER.json FEEDER.json` lists what they lack (link witness, picture IDs, retirement cookies, decoder completion, a calibrated clock). The test fixtures exercise the arithmetic only.

## Output rate following the source: source read and TV test (2026-11-24)

Ledger row "Output rate following the source". `SRC:` paths are relative to `lgtv/research/lgsrc/k/soc_GO/linux-and-kdriver_paluma-5/kdriver`.

**What the kernel can ask for is three rates, not any rate.** `_vsc_check_fr` (SRC `core/de/v4l2_vsc_event.c:2676-2718`) maps the source's `vFreq` to one of 48, 50 or 60: 25 and 50 fps (±0.5) give 50; 24 fps (±0.5) gives 48 only while the pulldown flag is set; everything else, including every rate above 55 fps, gives 60. `DE_IO_SetFrRate` (SRC `core/de/de_io.c:972-1000`) doubles it for this panel class and snaps the result to 96, 100 or 120 Hz, with 120 as the default for any other value. The MCU side selects a display-sync table entry from that number (SRC `core/de/mcu/io_video.c:1046-1059`, `:1555-1570`), so the request is a choice of sync-generator family.

**The 96 Hz after a Dolby Vision film is the pulldown flag.** `v4l2_vsc_update_pulldown` (SRC `core/de/v4l2_vsc_event.c:2130-2145`) sets it when the picture back end is given MEMC type 4 or 5 (`pullDown`, `cinema`; SRC `core/pe/v4l2_vpq_be.c:1813-1823`, names at `:2392`), which user space sets through the VPQ back-end control; the flag changing is itself a timing change for window 0 (`:2262-2265`), so the rate is re-picked at that moment with a source connected. 24 fps then asks for 48, doubled to 96 Hz. Without the flag the same 24 fps asks for 120 Hz and is shown 5:5. So the measured 95.5 Hz is the 96 Hz family locked to a 23.976 fps source (95.9 Hz), not a fourth rate.

**Fine rate inside a family comes from the lock, and its range is the open number.** The same call turns on DCO tracking unless free-run is forced (`VIDEO_CTRL_TRACE_DCO_FCW`, SRC `io_video.c:1053`): the output clock follows the decoder's frame clock, which is why 23.976 fps is shown at 119.88 Hz. The decoder's clock in turn follows the rate each picture is tagged with ("Tagged durations" above). The chain picture rate, decoder clock, DCO, panel therefore exists for an app's video; what the kernel source does not hold is how far and how fast the DCO follows (the tracking loop is in the DE firmware). A source at 27 or 58 fps is asked for as "120 Hz" by the kernel; whether the panel then runs at 108 or 116 Hz, stays at 120 with repeated frames, or loses lock is not readable from source.

What follows for VRR: there is no call that sets an arbitrary rate, and no reason to look for one in the kernel. The candidate is the lock itself. The output is an integer multiple of the source rate, and the three families sit at 96 to 120 Hz, so the nominal windows are 48 to 60 fps at 2x, 24 to 30 fps at 4x, and 96 to 120 fps at 1x under the HFR path; whether the lock reaches outside them (90 or 144 Hz at 1x) is part of the test. If the DCO follows an off-grid source across a window without muting, a stream's rate can be matched there; if it also follows a moving rate quickly, tagging each picture with its own duration is VRR in effect over that window.
