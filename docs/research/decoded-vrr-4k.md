# Internal 4K VRR: where picture timing survives

**No qualified internal 4K VRR path.** Fixed 4K120 decoding, a 144 Hz display mode, and a variable panel scan for each distinct decoded picture are separate capabilities. For the last one, both the right picture and an independently scheduled scan must be available. HDMI's range is not a measurement of the internal video path.

## What the stock path does

In LG's related O22 `kdriver` source, `core/de/v4l2_vsc_event.c:2204–2209,2224–2235,2266–2276,2411–2418` reads window 0's decoded timing and requests a mode when the source, dimensions, scan type or reported frequency changes. Frequency is derived from the picture's declared rational rate (`chip/o22/de/de_reg_o22.c:3412–3421`), not when it finished decoding. `core/de/v4l2_vsc.c:2434–2463` sleeps 40 ms between passes; there is no multi-sample dwell in that comparison and no hard 40 ms deadline. At 4K120 almost five pictures fit into one sleep. The one-second comparison in `core/de/de_io.c:1003–1009` throttles a **log message**, not a mode change.

For 67 and 72 fps the host selects the same 60 family (`core/de/v4l2_vsc_event.c:2688–2691`), doubled to 120 on this panel class (`core/de/de_io.c:988–999`). Yet [retail measurements](../lumagame-gaming-features.md#odd-rates-and-residue-follow-up-measured) found 67→119.81 and 72→143.84 Hz, at **1440p**, with tracking off. The 144 selection is downstream, not an ARM request for 144. Prior execution of the captured year-24 display-selector instructions (`0x50266a3c`, image SHA-256 `bc5aa595f350a0dc89f6f314c8cfe6977863ab021f7cda133bdf0795bbefd6de`) returned 144 for a stable internal 144 input with readiness zero, and 120 for the same input with forced readiness seven. That synthetic test used **144**, not 72. Neither it nor the 72 measurement establishes the exact 72-family threshold, its hysteresis, or physical lock time. In a separate [50-family transition](framerate-result.md#round-11-when-the-return-to-120-hz-happened), the output stayed at 100 after disconnect and returned to 120 on the next video's new timing; the 50 ms counter samples cannot resolve hardware lock time.

The archived *Game Mode Research* selector receipt (2026-11-01, `vrr-bounded-test-contract.json`) gives a stronger lead than the firmware strings: the normal-mode routine at `0x4001580d–0x4001583f` derives window readiness from **upstream source state**; a source-flag case can produce readiness 6 even when upstream readiness is zero. This does not establish a decoded app that supplies that flag. The source's HFR flag is not evidence for the display firmware's HRR flag. No stock app-level trigger for per-picture internal tracking has been established.

## Routes ranked for the 4K target

| Route | Evidence and decision |
|---|---|
| Stock app / video window | Lowest risk to study. Fixed 4K120 is measured. Above 2,764,800 pixels and integer codec or container rate ≥61, `core/vdec/vo.c:579–602` selects high-frame-rate (HFR) mode. `vds/vdisp_core.c:1078–1093` promotes an exact divisor of 120 or 100 to that family, otherwise keeps the initial rational; **either way** it fixes the timer. `vds/vsync.c:357–369` then ignores per-picture rate changes. A mode lock is not VRR. |
| Separately timed presentation of owned 4K pictures | [INFERENCE] Best development candidate for ≤120 distinct pictures/s: preserve each picture's timestamp and present it later with a fixed delay, independent of the delivery grid. It requires an enforceable surface lifetime, independent scheduling and bounded latency. Neither stock NDL nor the existing display firmware plan provides all three. Offline study is low risk; experimental display firmware is high risk. |
| Display-firmware-only tracking / ForceVRR | The display engine can follow the decoder timer. Retail 70/110 alternation followed the *mean*, not each picture. Switching forced mode off left state behind. Simply changing mode eligibility cannot recover dropped pictures or create an early ready signal. The [display firmware plan](rea-firmware-result.md#de-firmware-modification-route) is not a release path, and the signed decoder's presentation limit is upstream. |
| Decode to GPU / compositor | The documented copy produces 8-bit NV12 rather than native 4K HDR presentation. Stock graphics scanout is 1080p, fixed-grid, without an adaptive-flip interface ([source and measurements](../lumagame-gaming-features.md#decoded-frames-through-the-gpu-plane-source)). Not a 4K substitute. |

**4K144 and low-rate repeats.** The [captured decoder](rea-firmware-result.md) and related `core/vdec/vds/vdisp_core.c:55,264–277` and `vrate.c:565–575` establish the progressive 120 policy, independently of the display selector. A 144 Hz output can repeat pictures; 144 distinct 4K pictures/s is not established. The internal lower tracking bound, the safe transition into low-frame-rate compensation (repeating scans below that bound), and clean handback have not been measured. Neither an HDMI estimate nor an inferred firmware limit is a panel-care specification.

## Cheapest decision before firmware work

`core/vdec/vds/vdisp_core.c:480–505` copies `next_pts` only when another picture is already queued. `:966–978` selects the new frame and updates the display interface **inside the decoder timer callback**. `vds/deif.c:275–276` and `hal/de_ipc.c:275–277` forward PTS and next PTS; they do not announce an independent decode-completion edge. `vds/deif.c:156–165,328–338,578–592,645–655` treats HFR as ready without waiting for a display-read acknowledgement, defaults to two clearance slots and retires old frames. Slot depth is not a supported surface lease.

First check the existing input and diagnostic paths, not the TV. For one 4K stream epoch, keep source picture identity, its original presentation timestamp and tick rate, and local monotonic times for receive, feed acceptance, independently observed selection/availability, and last permitted use. Missing downstream events mean *unobservable*, not zero drops. A constant-rate encoded stream cannot distinguish adaptive presentation from fixed 120 Hz; arrival jitter alone is not variable source cadence.

For a delayed presenter, let `T[i]` be source presentation times mapped to a common clock, `A[i]` the first permitted use and `R[i]` the end of guaranteed ownership. A necessary interval for a constant delay `D` is `max(A[i] − T[i]) ≤ D ≤ min(R[i] − T[i+1] − tail[i])`, where `tail[i]` includes the required time after the next scan starts before the prior surface can be reused. A missing ID, unknown lifetime or unknown tail prevents a positive result. Passing this inequality for a capture does not prove independent scan scheduling, latency acceptability or panel VRR. Those need a matched variable/fixed control and synchronized controller and optical measurements.

For a later **passive mode check only**, an already-planned playback transition plus the existing main-window source report and bracketed `osd_irq` counts distinguishes the 100/120/144 families. No source launch, register access or debug setting is needed for that observation. It cannot prove on-glass per-picture tracking. No decoder runner, firmware load or TV action is part of this finding.

## LumaGame diagnostics boundary

For GFN, `gfn/engine/crates/opennow-streamer-platform/src/runtime.rs:500–508` has the sender's optional frame index, media timestamp and clock rate before pacing. At `:558–585` the VIDEO message gets the TV's monotonic handover time **instead of the media timestamp**. The engine remembers the association for up to 64 in-flight frames. `:387–402,429–440` correlates acceptance using that handover key, not the decoder's selected picture ID. The feeder rounds the key up to load-relative milliseconds, never decreasing it (`gfn/feeder/src/feeder.c:185–191`), then `gf_ndl.c:263–265` passes that integer to the player. Changing only the display firmware would not restore original source timestamps to this argument.

A diagnostics-only capture can join two fixed-size buffers without changing playback or the VIDEO protocol. On the engine side: load epoch, local sequence number, sender index with validity, raw timestamps and clock rate, keyframe/continuity, sink-entry, scheduled-release and actual handover times. On the feeder side: epoch, unrounded handover key, actual player timestamp, complete-message receipt, first feed call, final return, attempt count, queue depth and accept/drop reason (`feeder.c:383–406,1470–1487`). Both processes use the TV's monotonic clock; the sender media clock is a separate domain. Media deltas must account for wrap and discontinuities.

Ten seconds at 120 fps is about 1,200 pictures. Two preallocated 2,048-record buffers of 80 bytes each would cost 320 KiB in total. The capture must drop diagnostic records rather than stall the game, report omissions, and serialize outside the playback path. No stream content is needed. The [existing frame samples](../../game/crates/lumagame-feeder/PROTOCOL.md#app-lifecycle-channel) have arrival gap, feed delay, queue depth and reason, not a downstream per-picture completion. This capture can distinguish source cadence from local pacing; it cannot by itself pass the surface-lifetime or panel test.
