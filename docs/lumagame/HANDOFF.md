## Research results (settled)

- Low latency: NDL's game-mode load already applies every latency control; extra helper controls are redundant (docs/lumagame-gaming-features.md).
- VRR: the stock streaming path has not demonstrated per-frame panel refresh. Related O22 driver source can use a queued picture's rate to schedule the *next* decoder timer interval; that is neither arrival-triggered scan-out nor proof of panel tracking. The non-HFR path is a 1080p research candidate, not a 4K120 feature. Cloud G-SYNC stays off.
- 4:4:4 refused by VDEC firmware (signed); 120 fps cap compiled into signed vdec.bin. DE firmware is unsigned on O22 (plan only).
- LG Game Dashboard is HDMI-only with no app entry point; LumaGame draws its own overlay.
- Results: docs/research/rea-*-result.md and docs/lumagame-gaming-features.md.

## Native games (study of github.com/pustal/Web-Mario-64, 2026-11-15)

The standalone proof (a minimal C/SDL2/GLES 3 app, `org.nphil.lumagame.nativeproof`) was uninstalled and its source removed on 2026-11-23; it lives in history at `d9c9264405593749b567cf273753d906b2e73ac2`. It launched through This TV, displayed its triangle and returned automatically to LumaGame details. GLES 3.2 on Mali G52 reported 1920×1080; swap interval 1 was requested successfully and reported as 1. It completed 2,283 frames in 14.944 s (152.699 swap completions/s); intervals were median 4.904 ms, p95 12.654 ms, p99 14.355 ms, min 0.669 ms and max 19.411 ms, with no fallback marker. Swap completion is not panel refresh or proof of 120 Hz pacing.

The published compositor exposes no `wp_presentation` global; default `ClientCallbacks::Commit` is not flip or presentation feedback. Internal DRM flip timestamps require separate correlation, or optical capture, to establish panel cadence (`server/state.rs:349,375-387`, `kms/mod.rs:744-793`).

Native catalog refresh passed on the TV: This TV selection changed 1 → 0 → 1 in the same UI process, with stable toggle focus. The current app also passed 137 host tests and clippy.

Web-Mario-64 is a native webOS app (`type: native`), not a web build: Ghostship (an SM64 PC port) with a webOS patch layer, SDL2 2.30.12 from webosbrew's SDL-webOS fork (armv7), GLES 3 on the TV's own driver loaded at run time, packed as an ipk with `ares-package`. Remote keys map to SDL keys (Back 482, colour keys 486-489, Exit 505). Ghostship runs game logic at 30 fps with frame interpolation; its "match refresh rate" option should drive 120 Hz (read from code, untested). Plan for LumaGame's native engine: keep ports as separate SAM apps launched by LumaGame; first build a minimal SDL2 + GLES 3 app with a frame-time log, measure 120 Hz on the TV, then test the return-to-LumaGame handoff. LumaTV's own GPU path is rustui/render (loads `libGLES_mali.so` by path) with the 64-bit runtime in gfx64/.
