# Agent guide

Entry point for an agent working on LumaTV (this repository, formerly LumaGlass): how the parts fit, how a build reaches the TV and comes back off it, and the operational facts that cost time to learn. `HANDOFF.md` is the dated engineering record (installs, measurements, hashes); `plugins/` has one page per plugin; `../CHANGELOG.md` is the release history. Facts here are current state; anything unverified is marked [INFERENCE].

## Rules of the repo

- Commit and push straight to `main`, to both remotes: `origin` (GitHub) and `forge` (git.nateshome.net). No branches or PRs.
- The TV runs only a commit that is on `main` and pushed to both remotes. Installed binary hashes are recorded in `HANDOFF.md`.
- Before pushing: the touched crate's tests and `cargo clippy -D warnings` pass. No WIP, ignored tests or debug logging on `main`.
- Frame loop, input, video and power changes need a measured result (frame gate, video check) before claiming faster or fixed. "Accepted" means checked on the TV; untested cases are listed as untested.
- Surfaces and plugins take colours, glass, radii and type from the active theme's tokens only. Integrations are plugins: off until enabled in Settings.

## Component map

| Part | Where | Owns |
|---|---|---|
| compositor | `compositor/crates/lumatv-compositor` | The live Wayland compositor (64-bit, on LG's socket `/tmp/xdg/wayland-0`, started through a private glibc loader): scene, frames and refresh, input and key routing, video windows and scan-out, luna calls, panel dimming, OLED care. Runs the drawing engine that the UI's layers go to. |
| sm | `compositor/sm/lumatv-sm.c` | The 32-bit supervisor, bind-mounted over `/usr/bin/surface-manager`. Decides whether LumaTV runs, spawns and heartbeats the compositor (500 ms), bridges luna for it, and falls back to LG's compositor in place on a fault, an unsettled start or two consecutive failures. Home held 10 s is the owner's escape. |
| ui | `rustui/ui` (`lumatv-ui`), engine in `rustui/render`, wire types in `rustui/compositor-protocol` | The shell's logic as a 64-bit client with no GL: Home, Settings, panels, cameras, guide. It sends layers and groups to the compositor over a socket pair, gets keys over a key socket, and reads state from the helper. |
| helper | `helper/app` (`lumatv-helper`) | The trusted privileged process: a static aarch64 musl daemon running as root. Owns settings, weather and feeds, cameras, receiver, HA, BLE, the tuner host, the log collector and the plugin host. Loopback API on `127.0.0.1:18731`. Privileged work runs here, and only while its plugin is enabled. |
| dnd | `helper/app/src/dnd.rs`, `rustui/ui/src/dnd.rs`, doc `docs/dnd.md` | Do Not Disturb and snoozes: the helper's gate for camera pop-ups and plugin notes, the `dnd` topic and `/v1/dnd` routes, state in `dnd.json`; the UI's tile, status-bar mark, pop-up snooze sheet, held toasts and the drawer's missed group. |
| plugins | `helper/plugins`, `helper/denon`, `helper/app/src/*`, docs in `docs/plugins/` | First-party: `denon-receiver`, `scrypted-cameras`, `home-assistant`, `live-tv-tuner`, `guide-data`, `ble-proxy`, `tv-sensors`. Off until switched on in Settings, which asks first in the plugin's own words; the owner's approval of those words is kept in `plugins/enabled.json` (`firstParty`). Each plugin thread runs under `plugins::guard`: a panic stops that plugin alone and it retries after 30 s, doubling to 30 min. |
| lumatuner | `helper/tuner` | The antenna-tuner engine (HDHomeRun endpoints, M3U, XMLTV, slates). No host dependencies, so it can ship standalone. The helper's glue is `helper/app/src/tuner*`. |
| lumaxcode | `helper/xcode`, `venc/` | The engine that shares the TV's one hardware video encoder (jobs, one child process each, restarts, holds, events), with no host dependencies so it can ship standalone. The helper's glue is `helper/app/src/xcode/` (foreground-app gate, the child program's file, the shape guard); the child is `lumatv-venc xcode` (`venc/`), built into the helper for aarch64. Behind the Live TV Tuner's `?transcode=`, off until its setting is on. |
| tools/lumatv | `tools/lumatv` | The on-device command (POSIX sh, busybox) shipped in the IPK: apply, revert, boot hook, `compositor`, `helper start|stop`, `layout`, `wake`, `standby`. Must match the helper it starts. |
| gfn | `gfn/` | GeForce NOW stream engine and feeder (separate cargo workspace). |

How they talk:

- **ctl socket:** the compositor listens on `lumatv-control` in its runtime dir (`/tmp/xdg`), one text command per line, one JSON line back; client is `lumatv-compositor ctl --runtime-dir /tmp/xdg <cmd>` (`status`, `windows`, `journal`, `shell`, `switcher`, `key`, `remote`, `ring`, `refresh`, `vwin`, `fallback`; the UI's own commands go through `shell`, e.g. `shell show toast LumaTV:_text_with_underscores`). Local only. On the TV run it through the private loader in `/var/lib/lumatv/compositor` (`lib/ld-linux-aarch64.so.1 --library-path lib bin/lumatv-compositor ctl ...`).
- **Helper HTTP, 18731:** loopback only (non-loopback peers and unknown `Host`/`Origin` are refused); every write needs an `X-Luma-Client` header. A client reads `GET /v1/state` (carries `seq` and `boot`), then long-polls `GET /v1/events?after=<seq>&boot=<boot>` (at most 30 s); a client behind the 256-event ring, or from before a helper restart, is told to reset and reads the state again. `GET /v1/state/<topic>` reads one topic. A second listener on the TV's private address (`Mode::Lan`) serves MCP/AI clients with GET and POST only. The UI, the compositor and `tools/lumatv` all use this API.
- **Topics:** the hub in `helper/app/src/hub.rs` holds named JSON topics (`screen`, `receiver`, `weather`, `plugins`, ...); plugin topics are `plugin.<id>.<name>`. Setting a topic to the value it holds is silent. A topic whose only change on a poll is a top-level stamp (`at`, `updatedAt`) is set with `set_ignoring`, so the stamp alone raises no event: otherwise every poll puts the whole document into the ring and every long poll. Ring events keep their value as compact JSON text; `Event::data()` parses it. The UI reports its own state back with `POST /v1/ui`.
- **Logs:** producers send Unix datagrams to `/tmp/lumatv-log.sock`; the helper keeps at most 1 MiB in RAM under `/tmp/lumatv-logs/`. Tests cannot read the compositor's or helper's diagnostics from files.

## Build

Host is the Cody workstation; nothing builds on the TV.

- Environment for every cargo run: `TMPDIR=/data/home/tmp`, `CARGO_INCREMENTAL=0`, tests with `-- --test-threads 4` (or `RUST_TEST_THREADS=4`), `CARGO_BUILD_JOBS=8`; `nice -n 10` for release builds.
- Helper: `helper/build.sh test` (clippy `-D warnings` and host tests), `helper/build.sh` (static aarch64 musl into `helper/dist/`). It needs the LumaShow checkout at `/data/home/LumaShow/wt/lumatv` (path dependencies) and zig. The host CC and linker for the helper's build is `gfn/engine/tools/cc-host` (`cargo-zigbuild zig cc`, which rewrites the flags cc-rs passes). `rustui/tools/cc-host` is plain `zig cc` and breaks `ring`'s build; do not use it for the helper.
- Compositor, ui, sm and assets: `compositor/tools/build-tv.sh` produces the bundle `compositor/deploy` (`bin/`, `lib/`, `HASHES`, `cutover.sh`, `gate.sh`); it is not committed. Targets are aarch64 glibc 2.36 through `cargo zigbuild`. Per-crate: `cargo test -p lumatv-compositor`, `cargo test -p lumatv-ui`, each with `cargo clippy --all-targets -- -D warnings`.
- Disk is shared and capped. Use one scratch worktree per job (`/data/home/wt-<name>`) with its own single `target/`, build there, and delete the worktree and its target when done. Check `df -h /tmp /data/agent /data` first. Nothing installed may exist only in a scratch tree: it must be on `main` and on both remotes.

## TV access

- The TV is reached as root over SSH with paramiko: ed25519 host key pinned (`RejectPolicy`, no key lookup, no agent). Address and credentials live with the owner and are not in the repo.
- `luna-send` hangs without a PTY: open the channel with `get_pty()`. Use no PTY for binary-safe output and SFTP. `journalctl` hangs: read `/var/log/messages` (bracketed monotonic stamps, rotates within minutes). The userland is busybox; large programs go over bounded stdin (command under 1 KiB, chunks 16 KiB, Dropbear's receive payload is 32 KiB).
- Hold the lease before any TV-facing action: `/data/home/Marquee/tools/tv-lock.sh` (shared with Marquee). `acquire --why "<what>" [--ttl MIN]`, then `status`, `renew`, `release`; `with --why ... -- CMD` takes and releases around a command; `require` takes an implicit 10-minute lease if nobody holds it. The default TTL is 45 minutes (`PLX_TV_LOCK_TTL`); a lane is `PLX_TV_LOCK_LANE` and each session uses its own, never another's lease. The lock is a directory on the TV (`/tmp/plx-tv.lock`), cleared by a reboot, and times come from the host's clock. A lease cannot see a person watching: `acquire` prints IDLE or `IN USE` from what is in front, and `IN USE` means the owner says go first.
- Read-only while the owner is watching: with the panel on and anything but idle Home in front, or `IN USE`, do reads only (`ctl status`, screenshots, log and file reads). No keys, launches, setting, picture, volume, power or receiver changes. An agreed install is the exception; announce each step with a toast (`ctl shell show toast ...`) and leave Home in front and the receiver as found.
- The receiver is a Denon on HDMI 2 (ARC). Test runs mute it while on and leave it as found (off, unmuted). Its HTTP command page ignored `MUON` once; telnet on port 23 worked.

## Install and rollback

Install only a commit on `main` at both remotes, with its tests, clippy and release build green, from a `compositor/tools/build-tv.sh` deploy tree and `helper/dist`. Installs are quiet: a change reaches the set by the route that does not disturb what is on screen. Session scripts live under `/data/home/tmp/lumatv-*-<date>/`, outside git.

1. Hold the lease (`tools/tv-lock.sh`) and run the install under its renewal: `tv-lock.sh with --why "<what>" -- python3 compositor/tools/tv_install.py ...`. The tool refuses to install outside `with`, checks the lease again before each part, and only calls `require`, which never wakes the set. `with` inherits a lease the lane already holds; without one it takes it, which can wake the set, so take the lease first when that must be decided separately.
2. `python3 compositor/tools/tv_install.py --check` hashes every file the cutover installs (compositor, sm, libs, ui and assets, feeder, `recover-home.sh`, `logrelay.py`, `verified.list`, helper in both places, `tools/lumatv`, `tools/compositor.sh`) on the set and lists what differs, old and new, as 8-hex prefixes. Without `--check` it installs, and prints the same list for the `HANDOFF.md` section (date, main sha, hashes, what was and was not tested on the TV, how the set was left; commit and push it).
3. Each part goes in by its own route. The tools are backed up and replaced atomically (nothing restarts), then checked on the set (hashes, `sh -n`, `helper status` answers); a failed check puts the previous files back and stops before any later part. The helper is replaced (both copies backed up) and `tools/lumatv helper start` restarts only it; the install waits for a new pid that runs and is not unhealthy, and otherwise stops it, puts both previous copies back, starts them and says whether they came up. The ui alone (`cutover.sh ui-swap`) is replaced atomically, `bundle.manifest` follows it, and only the shell client restarts (`ctl shell restart`); the compositor keeps the app's surface and the video plane. The swap waits for the new client to be ready, with Home drawn when Home is in front, and puts the previous one back when it is not (a client that does not start at all ends the compositor and the supervisor falls back to LG's, so a ui must have passed the host gates). The backup of each replaced binary lands in `--backup-dir` as `<name>-<8 hex>`.
4. Anything of the compositor class (compositor, sm, libs, feeder, scripts; the ui rides along) is staged in `/var/lib/lumatv/compositor/staged` with a manifest of hashes. Nothing applies it by itself except the next boot, before the compositor starts. Without `--now` it waits there for the boot (`tools/lumatv staged status`); no watcher applies it at standby, because a compositor switch with the panel in Active Standby is not proven to leave the panel off. `--now` applies at once, under the lease, only with the panel on (`Active`), Home in front and no video app or game; otherwise exit 10 and the set stays staged. An apply is the cutover's `disable`, `install --delta`, `probe`, `enable` and the video check, run once, and any failure puts the previous files back (`staged/journal` holds the old and new hashes and the outcome). A new build whose video check shows no picture is rolled back, and the check is repeated on the restored build: only a picture there blames the new build (exit 1); no picture (exit 12) is the set's video path, which the new build is not shown to have caused, the previous files are back, and rebooting is left to the owner (`reboot` over SSH, in the foreground), then `tools/lumatv video-check`; a check that did not run blames nothing.

   A boot apply has no probe or video check. It checks the bundle and that the boot decision is unchanged, then stays pending with the previous files kept (`staged/prev`, `staged/judge`). The next boot puts them back, before the compositor starts, when the supervisor's records show the run went wrong (`running` not cleared after two minutes healthy, `failures`, `last-fallback`, `stock-ui-held`); a power cut within those two minutes counts as a failure. The run that went wrong happened first, on the supervisor's own fallback to LG's compositor, and the previous files return only at the next boot. Only `tools/lumatv staged accept`, run by hand, confirms the run and drops the previous files. It needs the panel on (`Active`) with Home in front and no game, no failure record, the compositor live with its shell ready, and a video check on the package's clip (`payload/feeder/check.h264`, which must exist) that shows a picture; a skipped check is no proof, and any shortfall keeps the previous files (exit 10 not now, 12 no picture, 1 not confirmed). While one is pending `tv_install.py` writes nothing (exit 4; `--check` still reports) and no staged set applies. `tools/lumatv staged apply --standby` exists for a proof run of the standby path by hand, with the owner's agreement, and is never triggered.
5. The old full install (`cutover.sh disable`, `install`, `probe`, `enable` from `/tmp/lumatv`, then `helper start`) still works for a first install or a recovery; `enable` is refused with exit 5 on a firmware not in `compositor/firmware/verified.list`.

Rollback: `cutover.sh disable` returns LG's compositor and Home (`revert` also removes the overlays); the supervisor falls back by itself on a fault; Home held 10 s is the owner's escape. To go back one build, install the `backup/` binaries by the same routes. A firmware update clears the mod and needs a new gate pass; the TV is webOS 10.2.1-5202.

After installing or trying any other app on the set (LumaGame, Marquee, a test IPK), run `tools/lumatv video-check` with the panel on; exit 12 is the same reboot.

## Frame gate

`compositor/tools/tv_gate.py` (on the set, `compositor/deploy/gate.sh`) runs the compositor as a session and measures, per surface (Home d-pad, Home widgets, Apps grid, quick settings, Settings scroll, keyboard, input picker, switcher), cycles of open and move: dropped frames above 10 ms at 120 Hz, first frame, burst end (limit 180 ms) and frames over 20 ms, from a kernel trace. `--only frames --refresh 120` is the 120 Hz check; `--frames-quick` the short set. A run whose trace ring overran fails `trace_complete`. The gate (`docs/research/perf/gate.py`) snoozes every camera's alerts for the run and puts the owner's snooze back as found, also on error, Ctrl-C or kill (not Do Not Disturb: turning it on empties the missed list); a capture with a pop-up, note or toast in it (helper feed, shell state) is discarded and re-run up to twice, and the summary prints `DISCARDED n capture(s)` with the reasons; one disturbed every time fails `undisturbed`. It leaves the refresh policy to `gate.sh refresh auto` at the end.

Pitfalls:

- A single Back on Home does nothing and a Back held 600 ms opens the task manager (the app switcher), so the wake's Back is harmless. The gate refuses to run while the switcher is up, the ctl does not answer, or the refresh is not held at the asked rate (30f333f3).
- An unprompted real camera pop-up or full view on screen during a run belongs to a real camera, not the test: exclude those cycles and rerun. The gate turns pop-ups off before its surfaces and back on after.
- After a Dolby Vision page `DE2VSYNC` can sit at 240 a second while `osd_irq` stays at 120, and the gate refuses to start; a few seconds of Live TV clears it.
- A full host disk mid-run logs results late; check `df` first.

Status (2026-11-09, main 6f9df990): Home d-pad and Home widgets drop 0 or 1 frames with no load; a run's first key can still miss the first-frame limit. Nine cycles per surface at 120 Hz, dropped frames: with no load, Home d-pad 1, 0 and 0 in three runs (the 1 on the first key after the install), Home widgets 0 and 0, Apps grid 1 and 1 on 752ab5f9; under plugin load (the tuner streaming about 11 Mbit/s, camera test pop-ups, a guide refresh) Home d-pad 1, Home widgets 2 then 0, Apps grid first frame up to 1442 ms (b6f72b77: 87, 7, 3 with no load; 63, 10, 1444 ms under load). The gains came from no longer drawing a frame over one waiting behind the flip in flight (752ab5f9) and from keeping a motion's unchanged first frame without a flip (6f9df990, which changes no picture and no timing); `6e47df5a` (UI at nice -10, helper threads and plugin processes batch) is hardening only. Do not claim a smoothness fix without a gate run under load.

Open, in this order (timeline and receipts in `HANDOFF.md`, 2026-11-09):

- A run's first key: after the install its commit carried 654 ops and the tick that planned it took 12 ms (one drop, first frame 813 ms); a later run's first cycle took 65 ms against a limit of 50.
- Under load, Home drops fall where a camera pop-up claims or releases the video window, with frames at 13 ms to GPU done.
- The Apps grid's first frame under load: nothing flips from the key until a camera pop-up arrives or leaves (104 to 518 ms late).

## UI scene limits

The engine accepts at most 512 layers, 256 groups and 64 motion tracks per client (`rustui/render/src/session.rs` `Limits::layers`, `compositor-protocol` `MAX_GROUPS` and `MAX_MOTIONS`, mirrored by `rustui/lumashow-ui/src/limits.rs`). A frame that would exceed them is refused (`more than N layers|groups`, `scene is full`) and the page loses what did not fit, typically the focus plates and the profile chip, until the UI's self-heal redraws; the UI's log line for a failed build ends with what is left of each ceiling and, for a full scene, which one it met. The shell's measured use (2026-11-09): Home at rest 101 layers, 44 groups and 10 tracks; the most, 178 layers and 13 tracks as Settings comes up over Quick Settings and 68 groups with Quick Settings over Home. A group or track that does not exist costs nothing per frame; the compositor's maps are sized for 112 groups and 56 tracks and grow past that. Settings opened over the quick panel still closes the panel (96797d97); a new overlay releases its groups when something opens over it. After any UI change, a TV check reads `ui.refusals` (must stay 0) and greps the logs for `compositor refused:` and `scene is full`.

## Video rules

- A camera pop-up uses no hardware decoder and no video window while an app other than Home or LumaTV is in front (f4c0ffa8): its picture is the compositor's texture, or stills with textures off, and a granted pop-up window ends when such an app comes forward (reason `app-front`). Holding the sub window's decoder over Netflix's browse screen made the next 4K Dolby Vision title fail with Netflix errorCode 600.
- A video window follows LG's decoder policy, which can take the decoder back; anything that claims one must tolerate losing it.

## Receiver keeper

With `denon-receiver` on and the receiver as the TV's sound output, the helper keeps the receiver on for the whole time the screen is on (`helper/app/src/receiver.rs`, `Keeper`). The output it keeps is remembered in `<data>/receiver-output.json` (`receiver_sync::Intent`), because LG saves `tv_speaker` itself about 1 s after the receiver leaves ARC: a `tv_speaker` saved while the receiver is not on keeps the receiver, one saved after it has read on for `hideAfterMs` releases it. A wake, or a helper start with the screen on, sends `ZMON` to a receiver not read as on; from `powerOnMs` (5 s) after a power command a receiver read as off is powered on again (backoff to `maxBackoffMs`, 30 s, for as long as the screen is on) and set to `SITV` once it reads on; switched off by hand it gets one more `ZMON`. Unreachable or still off, the live route moves to the TV speakers until it reads on. Nothing powers it on while the screen is off. LG's CEC wakes the receiver only when its last output was ARC (`Last ARC(1)` in the TV syslog). See `docs/plugins/denon-receiver.md`.

## Tuner

`live-tv-tuner` (docs in `plugins/live-tv-tuner.md`) serves a one-tuner HDHomeRun on port 5004, private networks only. With its messages on, a request for a tuner in use is answered 200 with 6 s of a slate naming the holder (Plex recording a programme, another client, or the TV's own Live TV), then ends; with them off it is 503 `805`. `GET /status.json` names the holder (`ip`, `name`, `channel`, `channelName`, `since`) or `{"holder": null}` without tuning. A request from the same client address as the current holder takes the tuner over (the earlier stream is told to end); another client's running stream keeps it (`helper/tuner/src/stream.rs`, `Tuning::take`).

## Phone remote

`phone-remote` (docs in `plugins/phone-remote.md`, engine crate `lumaremote` in `helper/remote`) listens on port 18733 of the private address while on. The compositor's `phone text` and `phone edit` work only inside `phone session on`, which the helper holds only while the plugin is on and a paired phone's session is live; keep that gate when adding verbs. Pairing opens only through the AI gate's `pair_phone` prompt (OK on the physical remote), and its routes take writes only from the TV's own UI (`X-Luma-Client: lumatv-ui`). `lumaremote vectors` regenerates `helper/remote/tests/vectors.json`, which the Swift kit also runs.

## Beszel

`beszel` (docs in `plugins/beszel.md`) runs Beszel's released agent from `bin/beszel` as uid 19999 while on. The agent's version must match the hub's: bump `VERSION` and `SHA256` in `beszel/fetch-agent.sh` with the hub. ## Home Assistant gateway

`ssgw` (docs in `plugins/ssgw.md`, engine crate `helper/ssgw`) runs the Rust gateway for port 3001 as uid 19998 while on, behind xinetd's entry as `tools/ssgw.sh` binds it; `ssgw-accept` hands every connection the gateway does not take to LG's `nsl`. Crash records are in `/var/lib/lumatv/ssgw/crash/` (`latest` names the newest). Connections that fell back to LG's gateway are in `/var/lib/lumatv/ssgw/fallback/` (one file per run of the same reason, with first/last time and count). `lumatv ssgw off` is the escape: it switches the plugin off and gives the port back to LG's entry without the helper.

## Foreground priority

The helper's `app_priority` (`helper/app/src/app_priority/`) is core behaviour, not a plugin: it runs whenever the helper does and is meant to become the TV's one memory and priority manager. It follows Android's process states. SAM's front list (`getForegroundAppInfo`) and life status (`getAppLifeStatus`) are subscribed; `getActivePipelines` names the apps playing audio.

| Android | Here |
|---|---|
| top / visible / perceptible `oom_score_adj` 0 / 100 / 200 | the app in front, other apps on screen, apps holding an audio pipeline: `min(original, band)` |
| cached 900–999 by LRU | apps behind: 900 + 10 per newer cached app, capped at 999 |
| `background` cpu group, `cpu.shares` 52 | `cpu,cpuacct/lumatv-background`, shares 52, made on first use and removed with the last |
| cached-app freezer, 10 s debounce | the app's own `freezer/<appId>` group 10 s after it left the screen; thawed at any status but `background` |
| trim before kill | `memory.soft_limit_in_bytes` 0 on cached apps; under medium pressure `memory.force_empty` on the oldest frozen app, once per cached spell |
| lmkd PSI mode | one `/proc/pressure/memory` sample a second, only while a cached app could be closed |

Closing follows lmkd's low-RAM defaults (`pressure::Tuning`): a full stall of 700 ms/s closes at once; otherwise a partial stall of 200 ms/s for two samples in a row plus one of lmkd's reasons (swap free under 10%, free pages under the high watermark, or file refaults at 30% of the file LRU, decaying by 50% while lmkd's would). The victim is the oldest cached app, the larger first on a tie; it is thawed, closed through SAM `closeByAppId` and named in a toast. One close at a time (the next waits for its processes to exit or 3 s, then 100 ms), three a minute at most.

Never touched: LG apps (`com.webos.`, `com.lge.`, `com.palm.`), LumaTV's apps (`org.nphil.`, the brand), anything not in SAM's running list (services, media and audio daemons, the compositor, the helper), processes owned by root, apps without their own memory group. Apps playing audio or on screen are never frozen or closed.

LG's memchute serves by default (stock mode). Its kept lists (`KeepAlive`, `KeepOnLaunch`, `KeepOnLaunchEx`, `InputList`, `HomeGroup` from every `com.webos.memorymanager.json` layer) are ranked but never frozen or closed, `memory.swappiness` is left to it, and a group memchute froze is neither frozen again nor thawed (`app_priority/memchute.rs`).

### LumaTV's memory manager (replaces memchute; off by default)

`lumatv mm on` (`tools/mm.sh`) binds the shim `lumatv-mm` (`helper/mm/`, 32-bit C, built by `helper/mm/build.sh`, staged in `/var/lib/lumatv/mm/bin/`) over `/usr/sbin/memchute` and restarts `memchute.service`, so LG's unit and role run it. It refuses unless LG's binary has the pinned sha256, the shim would run (`--would-run`) and the bus would give it `com.webos.memorymanager` (`--probe`). The shim answers every caller itself (SAM's `setRequiredMemory` at once) and bridges to the helper over `/var/lib/lumatv/mm/bridge.sock` (`app_priority/mm.rs`, `manager.rs`, `levels.rs`). In this mode the engine admits launches (closes cached apps oldest first, third-party before LG's, never Home, LumaTV's or the kept lists, until usable MB clears the need + 120 MB), signals `thresholdChanged` and `clearContainers`, pushes `getCloseAppId`, sets `memory.swappiness` 10 front / 100 behind, makes the per-app groups and attaches SAM's pids, gates preloads while an `EfsTarget` app is in front and asks `/tmp/systrim` daemons to trim on each worsening level.

Fallback: with no helper for 10 s (60 s after its `bye` at a stop), missed pings or a name it cannot register, the shim unmounts itself and execs LG's memchute in place, leaving a record in `/var/lib/lumatv/mm/crash/` and a Home Assistant notice (`appPriority.notify`). Three failures in 10 minutes write `gave-up`: LG's serves until the next boot or `lumatv mm on`. Otherwise the helper swaps back by itself once Home is in front. `lumatv mm off` (also from the escape) hands back at once and removes `enabled`; `lumatv mm status` and `GET /v1/state/app_priority` (`memoryManager`) show who serves.

Every change is journalled in `/run/lumatv-app-priority/state.json` with the value it replaced and put back when the app returns, at the helper's stop, when either subscription is lost, and at the next start after a crash. `"appPriority": {"enabled": false}` in `helper.json` is a diagnostic off switch; the journal is still put back. State: `GET /v1/state/app_priority`.

Checks on the TV with an app in front and Marquee behind: `/proc/<pid>/oom_score_adj` 900 or more, `/proc/<pid>/cgroup` `cpu,cpuacct:/lumatv-background`, `/sys/fs/cgroup/freezer/<appId>/freezer.state` `FROZEN` after 10 s and `THAWED` at relaunch, `memory.soft_limit_in_bytes` 0, all back on return and after `tools/lumatv helper stop`.

### Game mode

`app_priority/game.rs`, on top of the policy. It starts when LumaGame (`org.nphil.lumagame`) or Punktfunk (`io.unom.punktfunk.client-webos`) is first on screen; SAM has no game category. Entry, in order: background apps that are not LG's, LumaTV's, kept by memchute or holding audio are closed through SAM with one toast naming them (none while the media server has not said who plays); their exit is awaited up to 3 s; Home's weather and news refreshes and the guide's downloads pause (`game::FEEDS`); then on a worker thread, checked for an abort between steps, `memory.force_empty` on the memory groups of the running apps left (not the game's, those on screen, those holding audio or LumaTV's), `compact_memory` and one `drop_caches` of 1. Each step logs what it measured itself (see the API below), not the change of `MemAvailable`. Nothing of the game is frozen, stopped or reniced, and pad-boost leases, Scrypted, camera pop-ups, lumatv-ui and LG's services are untouched.

It ends 5 s after the game left the front, and at once when the switch goes off, a lease lapses, `on: false` is asked, an entry step fails, the SAM subscription is lost or the helper stops: the worker stops at its next step and the paused work resumes. A closed app is not reopened. The switch is Settings › System › General › Game mode (`system.gameMode` in theme.json, on unless `false`).

`GET /v1/gamemode` and the `gamemode` topic: `{gameMode: {switch, on, app, since, memAvailableMb: {before, after}, steps: [{step, <measure>, ms, note}], lastExit: {reason, exitMs}}}`. `exitMs` is the time from the game leaving the front (Home or the next app coming up) to game mode's restore being done (worker stopped, feeds resumed), so a `left` exit reads about the 5 s grace; it is 0 when the game was still in front (switch off, `on: false`, lease, failed step). Each step carries the one number it measured itself, never the change of `MemAvailable` (the game allocates meanwhile): `freedMb` (close: the anonymous memory of the apps that exited; pause: 0; reclaim: the groups' charge released), `cacheMb` (dropCaches: page cache, buffers and reclaimable slab released) or `contiguousMb` (compact: free memory in blocks of 64 KiB or more, from `/proc/buddyinfo`, gained). None is negative. `memAvailableMb` is the system's figure before the first step and after the last, for context. `POST /v1/gamemode {"on": true, "appId"}` gives an app not on the list game mode for 30 s while it is in front, renewed by asking again; `{"on": false, "appId"}` ends it and keeps the automatic start off until that app leaves the front.

### Prewarm

`helper/app/src/prewarm/`, core, beside the policy. The apps behind the remote's buttons (Marquee, Netflix, Prime Video, Apple TV, Live TV) are kept ready in the background in the owner's order (`system.prewarm` in theme.json, `{"on": true, "apps": [ids]}`, on by default; Settings › System › General › Keep apps ready, left or right on an app moves it). The launch is LG's own preload: SAM `launch` with `preload: "partial"`, `launchHidden`, `noSplash` as `com.webos.service.preloadmanager`; `full` makes Netflix show itself. One launch at a time, first to last, only with the screen on for 20 s, Home idle for 5 s, no pixel refresher run (`refreshguard`), no game or game mode, nothing playing, and `min(usable_pages, MemAvailable)` staying at least 400 MB above the app's cost (measured 76-92 MB Netflix, 113-122 Prime Video, 32-40 Live TV; re-read after each launch). Below 300 MB the lowest-priority app that is out of sight and silent is closed, one per 5 s, and stays closed for 10 minutes; at most 3 launches per app per 10 minutes. The order also feeds `app_priority`'s pressure closes (`prewarm::KEEP`: unlisted apps first, then the list last to first). An app that shows itself or sounds when preloaded is closed and left out until the helper restarts. Marquee and Apple TV ignore the preload mode and come to the front, so they are not preloaded (`shows_when_preloaded`): once the owner has opened them they stay frozen in the background (relaunch 55 and 91 ms against 1.4 and 1.8 s cold), and the order protects them. Preloaded: Netflix 827 ms and Prime Video 559 ms against 1.7 and 2.3 s cold; Live TV 133 ms against 764 ms. Topic `prewarm`; nothing is written to disk.

## Picture modes

`helper/app/src/picture.rs`. LG keeps one SDR picture mode per input, and LumaTV, Home and every app share the input `default`, so the helper keeps two remembered modes there: `ui` (LumaTV and the apps' menus) and `video`. A video app in front for 1 s (`VIDEO_APPS`: Netflix, Prime Video, YouTube, Apple TV, Disney+, Max, Hulu, Peacock, Paramount+, Marquee, Plex, Jellyfin, Crunchyroll and the live-streaming apps; ids from the TV's app list; the front app is `app_priority`'s `front[0]`) uses `video` for the whole time it is in front, menus included; per profile `apps.video` of theme.json (`{"add": [ids], "remove": [ids]}`) edits the list, and LumaTV's own apps and games are never on it. In any other app, SDR video full screen on the main sink for 2 s (videooutput `getStatus`; `fullScreen`, or a rect that fills 98% of one side of the 3840x2160 panel, is centred and covers a quarter of it, so letterboxed and pillarboxed films count and a top billboard, corner or small preview does not) switches to `video`. 3 s with neither switches back. HDMI inputs and Live TV keep LG's per-input memory; HDR and Dolby Vision (their own range) are LG's; nothing switches while a game is in front (`gamemode` on, a named game first in `app_priority`) or LG's Game mode is in force. A mode change seen in the picture subscription while a slot is in force, other than the helper's own write and outside the 5 s after a switch (Filmmaker Auto Start acts then), becomes that slot's choice. Mode writes are unpinned, preceded by a fresh read of the input and range, at least 2 s apart and at most 6 a minute; three writes that do not show within 4 s stop the switching for 60 s.

Presets write keys into an LG mode of their own (`PRESETS`: RTINGS Accurate in Expert Night, RTINGS Richer Color in Expert Day, LumaTV Vivid in Eco), pinned to `{pictureMode, input: "default"}`; keys the mode lacks are skipped. Each replaced value is journalled in `<data>/picture.json` before the write and `restore` puts the journal back exactly. No preset writes white balance or colour management, and none raises light output above the owner's Filmmaker (OLED pixel brightness 75, peak brightness off, contrast 85, dynamic contrast off); LumaTV Vivid keeps Energy saving Auto, which on this set only Filmmaker and Eco carry. The first run saves the mode in force as `video` and writes LumaTV Vivid for `ui`.

The switch is Settings › Picture › Separate picture for LumaTV and videos (`system.separatePicture` in theme.json, on unless `false`); off puts `video` back as the one mode. Topic `picture`: `{separate, active, ui: {mode, preset}, video: {mode, preset}, presets: [{id, name, mode, applied}], changed: [mode], context: {mode, input, range}, playing: {app, hdr, full}, front: {app, video}, hold, error}`. `POST /v1/picture/preset {"id"}`, `/slot {"slot", "choice"}`, `/restore {"mode"}`.

### Dolby Vision room mode

`helper/app/src/dvroom.rs`, on unless `system.dolbyVisionRoom` is `false` in theme.json (Settings › Picture › Dolby Vision room mode). While the picture's range is `dolbyHdr` it picks LG's `dolbyHdrCinema` (captioned Cinema · Dark room) or `dolbyHdrCinemaBright` (Cinema · Bright room). A session starts when Dolby Vision comes into force, or when the video's app or the input changes under it, and ends after 10 s without it, so a seek or rebuffer does not end it. At the start the sensor is read three times a second apart: a median at 3 lux or below is a dark room (the dark room reads 1 to 3, the screen's blips 4 to 5), at 10 or above a bright one (above the lamp-lit evening's 6 to 8 and the curtained afternoon's 5); between them night is dark and day bright, night being the sun below the horizon at the weather card's place, or 19:00 to 07:00 without one. A session that starts in Game or Personalized leaves the mode alone; any other mode, Vivid and Standard included, is replaced. During a session the mode moves only when the 30 s median stays past the far edge of the band for 2 minutes, at most once every 15 minutes, and time of day alone never moves it. A mode change that is not the echo of the helper's own write (the same value within 10 s) leaves the mode to the owner until the next session. The write is `pictureMode` alone, pinned to `{input, dynamicRange: "dolbyHdr"}` after a read finds Dolby Vision still in force; nothing else is written. The sensor is read only during a session (every 5 s). Topic `dvroom`: `{on, session: {app, state, mode, auto, lux}, error}`, `state` one of `starting`, `auto`, `hand`, `owner`, `refused`.

## Auto brightness

`helper/app/src/autobright.rs`, off unless `system.autoBrightness` is `true` in theme.json (Settings › Picture › Auto brightness, beside OLED pixel brightness, and the Quick Settings tile of the same name beside the OLED pixel brightness tile). The sensor is pqcontroller's `getInfo {"key": "eyeQLux"}`, the light sensor LG's Energy saving Auto reads: whole lux, about 28 ms a call, no subscription, so it is read every 2 s while the switch is on and the screen is lit. Measured at night: 1 to 3 in the dark (the screen's own light gives 4 to 5 blips), 6 to 8 with a lamp on, 2 to 4 with it dimmed. There is no sysfs light sensor or backlight on this set.

The controlled setting is OLED pixel brightness (`picture.backlight`), never black level (`picture.brightness`). The light filter uses 6 s and 30 s weighted means with separate brighten and darken delays. In SDR, the active profile’s corrections bend the default light curve for the input and picture mode. Repeated choices can distinguish gaming, browsing and playback, app and local time. A run of slider changes settles after 5 s and counts once. Reset learning applies only to the active profile. The curve and ramp are described in `docs/research/auto-brightness-research.md`.

Auto brightness holds LG Energy saving Auto off while driving the backlight; fixed energy-saving caps are left alone. SDR games use the same controller, not a second writer. HDR, Dolby Vision, unknown range, screen off and the compositor’s panel-dim ownership exclude automatic adjustment. The restore journal (`autobright.json`) is separate from training history: release restores owned settings without overwriting a subsequent manual change.

## Test events

`POST /v1/cameras/event` fires a test pop-up only with `cameras.testEvents` in `/var/lib/lumatv/helper.json`; otherwise it answers 403 `test_events_off`. Tests that turn it on must put `helper.json` back as found, restart the helper (`tools/lumatv helper stop`, `helper start`), clear the pop-up (`POST /v1/cameras/popup/clear`) and confirm a test event is refused. Leaving it on makes pop-ups appear unprompted and spoils the next frame-gate run.

## Device facts

LG OLED65C4PUA (model code `o22n2`), webOS 10.2.1 build 5202 (`10.2.1-5202`), firmware 33.22.52, MediaTek `O22A3`, 2 GB RAM, armv7 userspace with an aarch64 kernel, 120 Hz panel. Rooted with Homebrew Channel. The compositor's persistent enable is allowed only on firmware builds in `compositor/firmware/verified.list`. A plain `reboot` returns powered on; luna `machineReboot` drops to standby and does not come back. Set-wide detail and the dead ends: `HANDOFF.md`, "The set" onward.

Quick Settings' signal chips (size, frame rate, refresh, VRR, range) read inputs from the source LG's Game Optimizer uses: `luna://com.webos.service.utp.extinputs` `getVideoInfo` and `getVRRInfo` (`{pipelineId, mode: "GameOptimizer", interval: 1000}`; `vrrInfo.frameRate`, `vrrType`), on the pipeline the input's broadcast binds. That service answers only for HDMI/external inputs: with Netflix in front `getVideoInfo` and `getVRRInfo` return -106 (no resource) and `bind` -101 (no active broadcast). Apps therefore keep `videooutput` `getStatus`; the panel's refresh is still counted from `osd_irq` in `/proc/interrupts`.
